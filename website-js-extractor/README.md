# Website JS Extractor

黑盒二采用 **独立 Chrome MV3 插件 + 本地分析服务**：用户正常访问已登录网站，插件收集部署 JS、嵌套引用和页面上下文，以 jshound 为基线静态提取 **URL、请求参数、Host、对应 JS 文件**。

当前只有设计文档，没有可安装插件、可运行服务或完成的能力验收。先验证黑盒二分析核心，再由白盒接入仓库正式构建资产；黑盒一继续独立提供真实请求证据。

## 使用流程

```mermaid
flowchart LR
    A[启动服务与插件任务] --> B[正常登录和操作页面]
    B --> C[当前脚本快照与持续收集]
    C --> D[嵌套引用补抓与缺口]
    D --> E[冻结快照并离线分析]
    E --> F[四项主表与右侧证据]
    F --> G[Excel / JSON / 资产包]
```

新任务自动接入当前浏览器所有窗口中的 HTTP/HTTPS 网页及后续新网页，不要求选择标签页；插件图标打开管理标签页。用户可暂停、恢复、停止，并生成固定版本的分析快照。服务暂时不可用时仍可收集和导出任务包。

| 要分析的内容 | 做法 |
| --- | --- |
| 业务代码直接请求 | 识别最终发送机制和绑定 |
| 依赖/埋点 SDK 自行上报 | 分析依赖内部，不要求存在业务调用者 |
| 多层 JS 引用和函数封装 | 资产图与调用追踪分开；脚本获取默认至 D3，内部函数不共用三层限制 |
| 请求追加、修改或删除 | 合成 client 配置、调用参数及可确定的 hook/序列化，隔离实例和调用变体 |

插件取到的 JS、静态推导结果与浏览器实际发送是不同证据。缺脚本、动态配置、复杂混淆和未知副作用明确列入缺口，不承诺一次加载覆盖全站。

## 实施顺序

**S0 设计/样本冻结 → S1 真实采集原型 → S2 jshound 基线 → S3 最小插件链路 → S4 复杂请求恢复 → S5 稳定发布与白盒接入。** 每阶段的产物、可演示效果和通过条件见[实施计划](docs/plan.md)。

未来实现分别放在本工程的 `extension/`、`service/`，协议在 `contracts/`；依赖不放到根目录或黑盒一工程。本轮不建立空代码框架。旧黑盒一 JS 探索服务已删除，不作为兼容后端。两插件调试连接可能冲突，需明确报告并现场验证。
