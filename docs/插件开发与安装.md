# JS 请求采集插件开发与安装

按《[JS 请求采集浏览器插件](JS%20请求采集浏览器插件.md)》实现的独立 Manifest V3 扩展。EASYapi 与 maksimu/openapi-devtools 用于参考；未将其发现结果计数或主动过滤逻辑作为采集入口。

## 构建与安装

构建环境使用 Node.js `20.19+` 或 `22.12+`（Vite 7 要求）。插件的公开依赖使用 npm 官方源；`browser-extension/.npmrc` 仅对插件工程生效，并保留锁文件中的下载地址，不修改全局 npm 配置。

```bash
# 从 js-security 仓库根目录开始
cd browser-extension
npm ci
npm run build
```

如果先前安装报内部镜像 `rollup-*.tgz` 的 E404，拉取最新功能分支后，进入 `browser-extension/` 重新执行 `npm ci && npm run build`。`vue-tsc: command not found` 是依赖安装中断的后续错误，不需全局安装 `vue-tsc` 或删除锁文件。在 `browser-extension/` 内也可单次明确指定源：`npm ci --registry=https://registry.npmjs.org/ --replace-registry-host=never`。如果环境要求所有依赖必须走企业镜像，应由镜像维护方补齐锁定版本，再按组织约定调整项目配置。

Chrome 125+ 打开 `chrome://extensions`，开启开发者模式，选择“加载已解压的扩展程序”，选择构建后的 **`js-security/browser-extension/dist/` 目录**。交付 ZIP 解压后，选择包含 `manifest.json` 的目录。企业策略必须允许加载该扩展。

**已有用户先检查升级路径。** 此前从仓库根目录 `dist/` 加载的扩展，不应直接假定更换为 `browser-extension/dist/` 后仍能看到旧任务。没有固定 manifest `key` 时，已解压扩展的加载路径变化可能改变 Chrome 扩展 ID，而 IndexedDB 按扩展来源隔离，不自动迁移。

- 要继续使用原扩展的数据：先导出已有任务，构建后将新的 `browser-extension/dist/` 内容完整复制到原已加载的 `dist/` 目录，再点击旧扩展“重新加载”，保持原加载路径。源码和依赖仍全部在 `browser-extension/`，原路径只用于临时兼容安装。
- 要从新目录独立加载：先在旧扩展导出已有任务，并保留旧扩展；不要在确认备份前卸载旧扩展，以免删除其本地证据。新扩展不会自动读取旧扩展的 IndexedDB。

详见[界面、交互与升级改进记录](插件界面与交互改进.md)。

点击浏览器右上角插件图标，直接打开完整管理标签页。点击“新建采集任务”，以浏览器为采集范围，自动接入当前浏览器所有窗口中已有和之后新打开、导航到的 HTTP/HTTPS 网页；无需选择或管理标签页。可在单行过滤框输入网址关键词或 `domain:`、`method:` 等属性，空条件表示全部请求。检查归并和归档策略后开始。关闭管理标签页不会主动停止后台任务。Chrome 会显示 debugger 调试提示。

暂停不接收新请求，在途关联继续；恢复登记中断窗口。停止先进入“处理中”，默认等待 5 秒，在途超时登记不完整，再完成写盘。单页调试断开或页面关闭会登记该页缺口，其余页面继续。后台重启会中断任务；手动恢复后不补写中断时段的请求。

## 浏览器范围与留存

新任务统一使用浏览器级范围，覆盖当前浏览器所有窗口中已有和之后新打开、导航到的 HTTP/HTTPS 网页，不要求用户逐一选择或管理标签页。没有符合条件的网页时也可开始，任务等待网页出现；浏览器内部页、扩展页和其他协议跳过。该模式是对开始后可观测网页活动的采集，不读取或回补浏览历史。

新任务不再提供指定标签页范围选项，需要限定业务页面或接口时配置 Filter。为兼容历史数据，旧任务没有记录范围模式时仍使用原指定集合；恢复不会自动扩大到当前浏览器全部网页。如需采用新范围，结束旧任务后新建任务。

浏览器范围负责自动接入各个网页，Filter 决定请求是否匹配；默认 `matching` 留存命中及无法判定记录，并保留排除统计。过滤页只使用一个搜索框：空框保存全部请求，多个条件用英文分号 `;` 分隔。用 Filter 限定页面和请求，不要求为了过滤而逐一勾选标签页。

新网页必须先建立调试连接再订阅事件，因此首次导航的开头可能无法观测；这类动态附加缺口会留账，不承诺自动补齐。单页关闭或附加失败保留该页原因，其他页面继续采集；并不把单页问题等同于全部任务结束。暂停期间不接收新请求，也不附加新页面；恢复时重新检查当前浏览器所有窗口的网页。历史任务继续保留自身的原范围。

## 工程目录与查看流程

插件的源码、依赖、构建与测试完整隔离在 `browser-extension/`，其他方案可使用自己的目录；主仓库的 `docs/` 和 `references/` 继续共享。

```text
browser-extension/
├── package.json / package-lock.json / .npmrc
├── index.html / vite.config.ts / tsconfig.json
├── public/manifest.json
├── src/                 # 后台、管理页、详情侧栏、采集与数据模块
├── tests/               # 核心、转存、CDP 与页面交互验证
└── dist/                # 构建产物，不提交到 Git
```

请求工作台使用固定高度的可滚动列表。点击请求行或“查看请求”按钮，右侧立即打开详情侧栏，不需要滚动到列表底部。侧栏按“概览 / 参数 / 请求头 / 请求体 / 响应头 / 响应体 / 调用栈 / 原始数据”分类，支持复制 URL、复制保存内容、导出单条请求及查看采集缺失原因。概览同时展示响应 MIME、协议、远端地址、缓存来源与传输量。调用栈页使用 Chrome DevTools 的 `Request call stack` 与 `Request initiator chain` 两个分区，发起链中的其他请求可点击打开。请求组可打开代表记录，并返回本组全部原始观察。

管理页还提供任务设置、过滤规则、存储与转存、历史任务和使用说明。页面默认恢复当前扩展来源下的当前或已保存任务；自动刷新列表时保留已打开的详情及分类。“在途”视图可查看尚未终结的受保护请求快照，完成后更新已经打开的详情。正式交接前先停止并写盘，再导出任务包。本轮根因、状态控制与交互验证见[插件界面与交互改进](插件界面与交互改进.md)。

## 调用栈采集与查看

采集会话请求浏览器保留最多 `200` 个同步帧，并配置 `32` 层异步捕获；解析 `parentId` 时通过所属 debugger 会话读取父链。管理页保留同步 / 异步分段及 `Promise.then`、`await` 等 `description`，显示段内函数、脚本和一基行列。原始数据保留 `parent`、`parentId` 与采集状态，便于核对是没有返回父链，还是补取失败。

详情中的 `Request call stack` 按 Chrome DevTools Initiator 面板的行式布局展示函数名和 `脚本:行:列`，异步边界按浏览器返回顺序插入，不再把 script ID、debugger ID 或内部父链 ID 放在主视图。`Request initiator chain` 是请求 URL 关系树：从可取得的最上游请求到当前请求，并继续展示当前请求已观测到的下游请求；当前请求加粗，具有完整记录的其他节点可打开详情。Filter 排除的请求只为关系链保留原始 URL 和父关系，不保存请求头、正文或调用栈；紧凑节点计入任务容量，界面中不可点击。

重定向及 Initiator 自带 request ID 的关系按请求身份精确关联。普通脚本发起关系只有在同一标签页、调试会话和 loader 中 URL 候选唯一时才标为推定；多个同 URL 候选时保留“歧义”状态，不选择任意父请求。关系索引随请求落盘并按父 ID 查询，展开成本受可见链节点数限制，默认最多 `200` 个节点。关系候选未观测、尚未落盘或旧版本没有保存的请求会造成链缺口，界面明确说明。

为避免影响业务，Debugger 配置跳过全部暂停、不在异常处暂停；不能保证跳过暂停时关闭 Debugger、保留 Runtime 同步采集并标异步降级。请求 `200` 帧或 `32` 层不等于每个请求都能取得这些数量；当前父链解析限制 `33` 段（当前段 + 32 层异步父段）、`400` 总帧、`1,200ms` 和 `4` 并发。超时、帧数 / 层数限制、会话失效和不支持的命令都保留明确原因，不把有 `parentId` 但未解析的栈标成完整。

已有历史请求不会因升级而恢复当时没有保存的调用栈，需要重新触发场景。用户反馈的“DevTools 约 40 帧，插件只有 1 帧”须结合相同请求、捕获配置和异步段对照；本轮受控证据与限制见[调用栈采集与分段展示](插件界面与交互改进.md#调用栈采集与分段展示)。不承诺所有站点得到相同帧数。

## Filter 与归并配置

过滤页和新建任务共用同一个搜索框：

```text
orders                                         # URL 包含 orders
domain:api.example.com; method:POST            # 分号表示同时满足
resource-type:Fetch,XHR                        # 逗号表示同一字段任选一个
-resource-type:Image,Script                    # 前缀 - 表示排除
url:/\/api\/v\d+/i                            # 正则；i 表示忽略大小写
(method:POST OR method:PUT); status-code:200   # 括号和 OR 表示任选条件
page:"order detail"                           # 双引号包住带空格的值
header.Authorization:?                       # 问号表示字段存在
```

支持的字段是 `url`、`domain`、`path`、`method`、`status-code`、`resource-type`、`page`、`page-domain`、`referer`、`initiator`、`extension`，以及 `query.参数名`、`header.请求头名`、`body.JSON路径`。`字段:?` 表示字段存在，`-字段:?` 表示字段不存在。下方摘要即时说明实际含义；语法错误时显示原因并禁用开始、预览或应用。空框明确表示保存全部请求。

旧任务中的 Scope / Include / Exclude、嵌套 AND / OR / NOT 和常见匹配方式会转写成等价搜索语句，不再显示三段式编辑器或 JSON 编辑器。转写允许规范化内部结构，但匹配、排除和无法判定结果必须保持一致。

`dynamic_query`、`dynamic_json` 默认空数组，`uuid_path` 默认 false，不擅自忽略 UID、CNA、Token、租户或资源 ID。普通 Query 按名称稳定排序，重复名称的值不排序；JSON 对象字段可规范化，数组顺序不变。每条请求固定接收时的配置版本。

新记录不按字段名称脱敏。Cookie、Authorization、Token、Secret、Password、URL 用户信息、fragment、查询参数及请求体均保留浏览器可观测原值。每个任务提供两种字段值保存方式：“完整保留”不做字段值或正文长度截断；“自动截断”用于快速保存分析，字段名始终完整，单个值超过 64K 字符时保留约四分之三的开头和四分之一的结尾，正文超过任务字节上限时按 UTF-8 字节保留首尾片段。截断写入明确标记和原始长度。自动模式下 JSON 深度超过 32 层仍明确标记；历史记录中的 `[REDACTED]` 无法恢复。旧任务缺少该选项时按“自动截断”运行。

## 服务协议

在任务策略中设置 `service.enabled` 和 `service.url`，通过界面授权接收服务 origin。只接受 HTTPS，不允许 URL 内嵌凭据、Query 或 fragment，不跟随重定向。可选 Bearer Token 仅存 `chrome.storage.session`，不进入任务配置或导出包。

```http
POST /ingest
Content-Type: application/json
Idempotency-Key: <稳定批次ID>
Authorization: Bearer <可选会话令牌>
```

```json
{"schema_version":"0.1.0","batch_id":"...","scan_id":"...","records":[]}
```

服务必须按 Batch ID 幂等持久化；**持久化成功后**返回：

```json
{"batch_id":"相同批次ID","persisted":true}
```

HTTP 2xx、请求已经发出均不等于转存成功；缺少上述回执仍失败。自动最多 3 次尝试，指数退避下限，调度可晚于下限；耗尽后等待人工“重试失败批次”，原始本地数据保留。`service.interval_ms` 默认 5 秒（调度周期约 15 秒），`service.compress` 默认 false；开启后发送 gzip 和 `Content-Encoding: gzip`。每批固定接收地址及压缩选项。令牌失效后先重新授权。任务配置变更不会把已完成记录自动再发到新服务。

### 阿里云 SLS

任务的 `sls` 配置保存 Endpoint、Project、Logstore、接入模式和批次策略，不保存凭证。标准 Endpoint 填 `cn-hangzhou.log.aliyuncs.com` 这类地域地址，发送地址组装为 `https://<project>.<endpoint>/logstores/<logstore>`；自定义域名必须是无路径、Query、fragment 和凭据的 HTTPS origin。

推荐 `mode: "sts"` 并使用 STS 临时凭证。AccessKey ID 和 AccessKey Secret 始终必填；SecurityToken 只在 STS 临时凭证下必填，长期 AccessKey 没有 SecurityToken，可以留空。界面将签名凭证写入 `chrome.storage.session`，键由 Endpoint、Project、Logstore 组成；凭证不会进入 Scan、IndexedDB 请求记录、任务包或 CSV。浏览器会话结束、扩展会话存储丢失或 STS 过期后，失败批次保留，重新授权再手动重试。临时身份只授予目标 Logstore 的 `log:PostLogStoreLogs`。

“测试连接”会用当前配置和同一签名流程真实写入一条 `connection_test=true` 的最小日志，并显示 `x-log-requestid`。它同时验证 Endpoint、网络授权、签名、凭证、Project、Logstore 和 `log:PostLogStoreLogs` 权限；测试会在 Logstore 留下一条日志，不应描述为只读探测。

新建任务弹窗同时提供文件归档和 SLS 两个任务级开关。SLS 使用一份保存在 `chrome.storage.local.sls_profile` 的共享非密钥配置：设置页保存或测试成功、新建任务测试成功或创建成功都会更新该配置，之后的新任务直接复用。启用 SLS 后可填写接入方式、Endpoint、Project、Logstore 和会话凭证并执行连接测试；点击“开始采集”也会完成相同的 Endpoint 授权和凭证保存，因此连接测试不是创建任务的前置条件。AccessKey Secret 和 SecurityToken 只进入 `chrome.storage.session`，界面只显示脱敏 AccessKey ID 以及 Secret、SecurityToken 是否已保存，任何密钥都不进入共享配置、任务配置、IndexedDB 请求记录或导出包。

STS 请求按照 SLS LOG 签名规则生成 UTF-8 `Content-MD5`、`x-log-bodyrawsize`、`x-log-apiversion: 0.6.0`、`x-log-signaturemethod: hmac-sha1`、`x-acs-security-token`、`x-log-date` 和 `Authorization: LOG <id>:<signature>`。签名写入 `/logstores/<logstore>`；成功保存 `x-log-requestid` 作为批次回执。`mode: "web_tracking"` 写入 `/logstores/<logstore>/track?APIVersion=0.6.0`，不使用凭证，但要求 Logstore 开启公网匿名写入，不能当作可信来源。

新批次使用 `sls-2`：常用字段直接检索，复杂字段各自序列化，不再附带完整 RecordEntry。`sls.upload_fields` 独立配置上传字段，缺省使用推荐集合（排除 TLS、性能缓存与内部标识）；本地数据不受影响。请求/响应正文仅保存 `representation`、可选 `encoding`、`value_kind` 与单一 `value`；JSON/表单优先解析结构，重复 JSON 键、高精度数字或非法表单编码回退 raw。响应头不再重复上传 raw 文本。调用栈以本记录内 `scripts` 字典和 `url_ref` 去重，不删帧或异步父链。异常采集原因保留，成功说明缩为状态；移除固定 protection 说明及内部 group_key。

仅超大投影使用 `sls-2-chunk`：按 `transfer_batch_id + request_id + record_sha256` 分组，依 `record_chunk_index` 拼接 `compact_json_chunk`，校验 SHA-256 并 JSON.parse 恢复。普通记录无分片字段。多次 HTTP 的 `transfer_part_index/total` 放在标签中，仅多片时出现。旧批次没有 `sls_schema` 时使用冻结的 v1 序列化，保留 `record_json_chunk` 及原有重试内容；新建批次带 `sls_schema=sls-2`，目标与字段选择均随批次快照保存。

SLS 采用至少一次投递。HTTP 已被 SLS 接收但响应丢失、或多分片中后续请求失败时，重试会重新发送同一稳定 Batch，可能产生重复日志；下游用 `transfer_batch_id + request_id + record_chunk_index` 去重。插件自动最多尝试 3 次，非 2xx 响应正文截取至 300 字符显示，本地记录不会因远端成功而自动删除。启用 SLS 后会规划当前任务全部尚未进入 SLS 批次的已持久化记录，不只发送启用后的新记录。

## 导出和一致性

```text
EO_SCAN_<任务ID>/
├── scan_manifest.json
├── requests_0001.jsonl
├── request_groups.jsonl
└── capture_errors.jsonl
```

任务目录通过用户选择目录写入；最后成功写入 manifest 才显示成功。ZIP 的请求分片另有 SHA-256；CSV 嵌套字段为 JSON，公式前缀按文本保护。取消目录写入可能留下部分文件，界面明确报错，请勿将无成功 manifest 的目录作为完整包。导出到新目录可避免与此前同名包混淆。

分组记录有代表 ID，每条原始请求有 `group_id`；在原始视图搜索组 ID 可查全部成员。仅代表模式导出不可恢复逐次证据。Schema 为初版 `0.1.0`；Excel / `analysis.json` 下游导入和静态关联仍属于后续汇总模块，此版不生成虚构静态依据。
