# API 发现与统计：讨论结论

本文件记录用户与助手关于白盒、网站 JS 黑盒分析的讨论，作为后续方案设计依据；不表示相关能力已经实现。

## 1. 最终目标

用户最终需要所有前端 API 的统计信息，包括业务代码与第三方依赖引入的请求，以及 URL、Host、方法、参数和对应 JS。不能只提取容易识别的业务接口，遗漏 SDK 内部请求。

“所有”是覆盖目标；实际报告必须说明输入版本、构建配置、已获取资产、分析范围及缺口，不把已发现数量等同于全部数量。

## 2. 白盒：利用业务源码与依赖结构

白盒有源码、目录、依赖声明、锁文件及模块关系，应利用这些上下文组织分析，不能只把构建目录当作一批无归属 JS 扫描。

| 对象 | 分析方向 | 必须保留的限制 |
| --- | --- | --- |
| 业务代码中的 API | 优先从明确的接口定义、业务调用及已知请求封装提取，简单形态先产出 | 业务归属清楚不等于 URL、Host 和参数完整；动态配置、拦截器和深层内部封装仍需追踪 |
| 第三方依赖 / SDK 中的 API | 沿相关导入、资产引用和调用链深入，找到 SDK 内部发送点及请求构造 | 可能跨模块、嵌套 JS 或动态加载；不能只记录顶层 SDK 调用，也不能假定所有第三方实现都复杂 |

示例：`业务函数 → sdk.track → 队列/序列化 → sendBeacon`。需要找到 SDK 内部的请求，同时保留能取得的业务调用关系。内部业务封装也可能很深，分析深度按证据和缺口决定，不只按代码归属决定。

保留正式构建和构建产物核验要求，同时关联业务源码、依赖及构建资产。简单提取、依赖深入和构建结果核对之间的具体阶段协议仍需设计与验证；本次讨论不直接冻结实现顺序或算法。

## 3. 网站 JS 黑盒：统一分析，以 JS 发送位置归属

网站 JS 黑盒拿到部署脚本，统一分析已获取的 JS，**不要求先区分业务代码和第三方代码**，不将归属识别作为提取或计数的前置条件。

- 主要定位依据是包含底层发送点的 JS 文件、URL、内容哈希和可取得代码位置。
- 例如 `app.js → sdk.js → fetch`，底层发送位置属于 `sdk.js`；能够恢复 `app.js` 的上层调用时附上，不能恢复时保留缺口。
- 仅识别到封装调用或 URL 字符串时，不能伪称已经定位底层发送点。
- 有 source map、模块或依赖证据时可补充归属，但不影响无此信息的结果输出。
- 下载到的文件不等于全部线上 JS，收集缺失与分析失败需要分别登记。

## 4. 两路的共用与区别

可复用发送点识别、URL/Host 还原、参数追踪和证据表达等能力；不能因此认为白盒与网站 JS 黑盒是同一条完整分析流程。白盒应利用源码和依赖上下文，黑盒需要恢复部署脚本、打包模块与页面配置上下文。

JS 获取深度、打包内部模块层数与函数调用追踪深度分别统计。“递归深入”不能只实现为多下载几层 JS。

`fetch`、`XMLHttpRequest`、`sendBeacon` 是底层发送机制；业务接口函数、请求封装和 SDK 调用是不同层次。代码属于第三方，不代表请求一定发送给第三方；请求目标单独记录。

## 5. 统计口径

保留逐调用上下文/发送位置的底层记录，再建立接口汇总。共享发送函数可能接收多个业务接口，不能只按发送点计为一个 API。

- **接口分组数**：按明确且可追溯的归并规则汇总接口；同一接口出现在十处调用时可以归为一组。
- **调用上下文与发送位置数**：保留十处调用及其底层发送位置的关联，不用分组覆盖原始记录。
- **实测请求次数**：属于浏览器采集统计，不能混作静态接口数量。
- **候选、未解析项和资产缺口**：单独统计，不混入已确认接口数量。

Host、Method、路径模板及动态地址如何归并，跨版本和跨来源如何关联，仍需明确规则及反例验证；不能简单以 URL 相同合并不同版本、参数或证据。

## 6. 对后续方案的约束

后续方案必须说明如何利用白盒源码结构、如何从业务调用深入依赖、如何定位黑盒 JS 发送点、如何形成接口统计及暴露覆盖缺口。不能仅列出工具、AST、递归扫描等技术名词代替可核验的分析路径，也不能把“简单方法可覆盖大部分业务请求”写成“已能获取所有业务 API”。

本次只记录方向并修正文档口径，不增加实现完成项。当前工程状态仍以各工程说明及[白盒实施计划](../frontend-api-extractor/docs/plan.md)为准。
