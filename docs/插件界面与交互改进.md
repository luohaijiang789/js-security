# 插件界面与交互改进

本轮按用户实际试用反馈重做管理界面、采集范围与查看流程，并将插件工程完整移入 `browser-extension/`。构建、升级与安装步骤见[插件开发与安装](插件开发与安装.md)，工程入口见[插件 README](../browser-extension/README.md)。

## 已复现的问题

| 问题 | 复现或原因 | 本轮处理 |
|---|---|---|
| 点击接口看起来无反应 | 100 条请求时，详情在表格下方约 `7,259px`，而测试视口仅高 `1,000px`，点击没有把详情带入视口 | 使用固定高度列表与常驻详情侧栏；点击行立即显示详情，窄屏使用可见侧栏 |
| 重开后看不到已保存任务 | 后台重启后当前运行任务为空，页面未自动选择 IndexedDB 中的历史任务 | 优先恢复用户选择，缺失时选择当前或最近历史任务；后台暂不可用时仍可查看本地数据 |
| 刷新干扰查看 | 列表轮询和详情记录更新没有作为稳定浏览流程验收，可能覆盖当前选择或把详情分类归位 | 详情身份与内容更新分开管理；轮询保留已打开请求、分类及任务选择，过期响应不能覆盖新操作 |
| 新任务继承旧策略 | 编辑当前任务与创建新任务共用表单，可能携带旧任务 Filter 和有损归并配置 | 新建弹窗使用独立草稿，从明确的模板与归并策略开始，范围统一为当前浏览器的网页；取消不会改动已有任务 |
| 导出可能混入其他任务 | 长时间导出期间仍依赖可变的界面任务选择 | 导出开始时固定任务、配置与选中记录；写入期间锁定任务切换，取消与失败明确反馈 |
| 只有结束请求可见 | 长连接等请求没有终态前，用户无法查看已经取得的字段 | 增加“在途”快照视图，按批次展示受保护的已取得字段；打开的详情在请求完成后自动更新终态 |
| 新任务需要逐一勾选页面 | 采集范围与留存筛选混在一起，不便跨页面操作 | 新任务统一为当前浏览器所有窗口中的 HTTP/HTTPS 网页，自动延续新页面；无需管理标签，Filter 决定留存，旧任务恢复范围不扩大 |
| 目录占用了整个项目根部 | 插件的源码、npm 依赖和构建文件直接放在多方案仓库根目录 | 统一放入 `browser-extension/`，其他方案使用各自工程目录，主仓文档与参考仓继续共享 |

## 管理页与数据查看

点击 Chrome 工具栏插件图标直接打开管理标签页，不再经过 Popup。工作台包含原始、在途和聚合三个视图，提供全任务搜索、资源类型过滤、分页、任务切换和右上角导出入口。

详情侧栏分类展示：

| 分类 | 展示内容 |
|---|---|
| 概览 | 完整 URL、方法、状态、页面、Referer、发起脚本、时间、Filter 版本、采集质量及请求身份 |
| 参数 | Query 名称和值，保留重复名称、空字符串和原始顺序 |
| 请求头 | 已取得的头、脱敏观察和完整性原因 |
| 请求体 | 表示类型、Content-Type、解析内容；合法 JSON `null` 与未取得正文分别显示 |
| 调用栈 | 同步帧及异步父段分段展示，保留 `description`、函数、脚本及一基行列；缺失坐标、预算限制与未展开 `parentId` 保留说明 |
| 原始数据 | 全部已保存字段与状态，可复制 JSON 或导出单条 JSONL |

原始记录不会被聚合视图替代。点击请求组可查看代表记录、次数和差异，再进入本组全部原始观察。在途视图展示的是可能尚未到齐的受保护快照，不能当作完成请求；完成后保留同一请求 ID，并更新已经打开的详情。

## 调用栈采集与分段展示

用户反馈 Chrome DevTools 可看到约 40 帧并含 `Promise.then`，而插件只有 1 帧。现场具体缺失位置不能仅凭界面截图判定；需要比较同一请求的原始 CDP 数据、采集配置和异步父段。本轮补齐同步捕获深度、异步捕获配置、`parentId` 读取和分段展示，对受控样例验证，不把单次结果外推为所有站点的固定帧数。

| 环节 | 实现与边界 |
|---|---|
| 同步捕获 | 每个会话配置 `Runtime.enable` 与 `Runtime.setMaxCallStackSizeToCapture({size:200})`，保留请求时可观测的同步帧 |
| 异步父链 | 配置 `Debugger.setAsyncCallStackDepth({maxDepth:32})`；内联父链直接保留，引用父链由所属会话的 `Debugger.getStackTrace` 补取 |
| 业务执行 | 先设置 `Debugger.setSkipAllPauses({skip:true})` 再启用 Debugger，不在异常处暂停；不能保证跳过暂停时关闭 Debugger、保留 Runtime 同步采集并标记异步降级，不主动暂停业务 |
| 展示与原始数据 | 保留 `description` 分段，如 `Promise.then`、`await`，逐段显示帧、函数、脚本、行列及未解析引用 |
| 有界解析 | 最多 33 段（当前段 + 32 层异步父段）、400 总帧、1,200ms、4 并发；超时、上限、循环或会话失效保留已有信息及原因 |
| 完整性 | 捕获参数不是完整性保证；仅对 CDP 已返回、在预算内解析完毕的链标完整，不补写附加前或浏览器没有返回的历史 |

同请求原生 CDP 对照使用独立新建 target，避免 Playwright 创建页面时预先启用 Runtime 干扰基线。在 Chromium `154.0.8037.57` 上，固定样例 `checkout-stack-fixture.js` 使用 35 层 `checkoutDispatch` 递归，并通过 `checkoutPromiseLeaf` / `Middle` / `Root` 构造三层 `Promise.then` 及 `await`。结果如下：

| 捕获配置 | 同步请求的同步段 | Promise 请求的同步段 | Promise 请求的异步父段 |
|---|---|---|---|
| 仅 `Network.enable` | 1 帧 | 1 帧 | 未返回 |
| Network + Runtime 捕获深度 200 | 38 帧 | 37 帧 | 未返回 |
| Network + Debugger 异步深度 32 | 1 帧 | 1 帧 | 3 段 `Promise.then`，每段 1 帧；1 段 `await`，1 帧 |
| Network + Runtime + Debugger 配置 | 38 帧 | 37 帧 | 同上，Promise 请求全链共 41 帧 |

`38 / 37` 分别是两个请求的同步段帧数，并非整个异步链的总数。这个样例确认同步捕获深度与异步父链配置各自影响不同部分；不能仅靠启用 Debugger 就认为同步帧已补齐，也不能仅靠 Runtime 深度就认为异步链已取得。它解释了受控场景为何可能从 1 帧增加为多帧，不能据此认定用户所有站点的漏帧原因或保证固定数量。

固定测试见[调用栈原生 CDP 对照](../browser-extension/tests/call-stack-cdp.test.ts)。从仓库根目录运行：

```bash
cd browser-extension
npx vitest run tests/call-stack-cdp.test.ts
```

本轮调用栈对照的 3 项测试均已通过。真实 CDP 经采集器保存后，对函数、脚本 URL、行列、Script ID 与 `description` 逐项核对；JSONL 与解压后的真实 ZIP 保留相同调用链。受控业务执行期间未收到 `Debugger.paused` 事件，业务继续执行；新增原生会话验证先设跳过暂停再启用 Debugger，100 次 `debugger;` 均未暂停。生成报告位于 `browser-extension/work/browser/call-stack-cdp-result.json`，不作为源码提交。这里使用真实 Chromium CDP 与 fake-indexeddb，不等于企业环境真正加载 MV3 扩展的验收。升级前保存的单帧历史记录不能自动补齐，需要重新触发业务场景采集。

## 浏览器级采集与业务留存

新任务统一采集当前浏览器所有窗口中的 HTTP/HTTPS 网页，并自动纳入之后新打开或导航到的网页。用户不需要选择或管理标签页；阿里云等业务流程打开新页面后，采集按浏览器范围自动延续。任务可在零网页时启动等待，浏览器内部页、扩展页和其他协议跳过。默认匹配留存由 Filter 决定保存哪些请求；不会读取或回补历史浏览记录。

新任务界面不提供指定标签页模式，业务范围和接口留存通过 Filter 配置。后端仅为兼容历史任务保留原指定集合：旧任务缺少范围字段时，恢复不会因升级而自动扩大。单页关闭、导航到内部页或调试附加失败分别记录原因，不终止其他页面的采集。暂停期间不附加新页面，恢复时重新检查全部窗口的网页。

动态接入必须等待建立调试连接，首次导航开头可能遗漏；缺口会登记而不是宣称该次页面加载完整。范围管理、接入失败和动态页面行为需与页面展示分别回归，不能用已有六项查看流程测试替代新增范围行为的验收。

## 状态与并发控制

页面刷新、用户选择、打开详情和导出各自保留操作身份；旧异步结果返回时，先判断是否仍属于当前任务与当前操作。后台任务变更按顺序处理，避免重复开始、停止与恢复互相覆盖。后台周期写盘和转存调度分开，慢转存不会阻断在途快照写入。

导出固定本次任务上下文，选中在途快照时保留 `pending` 状态。正式交接仍应先停止并写盘，再导出完整任务包。界面的自动刷新开关只控制列表刷新，不表示暂停浏览器采集。

## 已有用户的目录升级

将源码放入 `browser-extension/` 不会自动迁移旧扩展的数据。没有固定 manifest `key` 时，Chrome 加载已解压扩展的路径变化可能改变扩展 ID；IndexedDB 按扩展来源隔离，因此从旧根目录 `dist/` 改为 `browser-extension/dist/` 加载后，旧任务不保证在新扩展中可见。

需要保留已有任务时，可选择以下一种方式：

1. **保持原加载路径更新。** 在 `browser-extension/` 构建后，将 `browser-extension/dist/` 的构建内容完整复制到原来已经加载的 `dist/` 目录，再到 `chrome://extensions` 点击该旧扩展的“重新加载”。原安装路径不变，可继续使用旧扩展来源下的数据；更新前建议先导出已有任务。源码、依赖和正式构建配置仍全部在 `browser-extension/`，原路径只用于临时兼容安装。
2. **新路径独立安装。** 先用旧扩展导出已有任务，再加载新的 `browser-extension/dist/`。在确认备份可用前保留旧扩展，不要卸载它，以免删除其本地证据。新扩展不会自动读取旧扩展的 IndexedDB；当前没有承诺跨扩展 ID 自动导入历史任务。

构建前先停止旧任务并完成导出。确认实际加载路径、扩展 ID 与需要保留的数据后再更新，避免把“新来源下没有历史记录”误判为采集数据库损坏。
