# 有界并发上传与分析可见性

本轮解决大JS上传阻塞后续小事件的问题。沿用capture-stream-2的任务、流、连续编号、摘要与封账语义，新增可协商能力delivery-window-1；捕获缺失、磁盘损坏和原始CDP日志仍不属于本轮完成范围。

## 协议和状态

插件先持久接纳，再查询/health。只有同时返回capabilities含delivery-window-1、delivery_window=64，才启用窗口模式；其他已支持旧协议的接收端保持串行。协商缓存按接收地址/项目隔离，新任务更换接收端时重新协商。网络/健康检查失败暂停并保留待传，不绕过持久接纳。

窗口模式在POST /events的信封增加delivery_mode=window-1，不修改已编号事件JSON及摘要，因此旧串行待传可以升级重试。同一流一旦进入窗口模式，后续新事件不能降回无mode的严格串行请求；存在乱序待确认时不支持降级旧服务器。

| 状态 | 语义 |
| --- | --- |
| 单条持久ACK | 该条原始事件、对象引用和账目事务已提交，可原子删除本地对应正文 |
| contiguous_sequence | 从1起连续确认/收到的前缀；不同于累计确认条数 |
| received_highest | 服务端当前已接收的最大序号 |
| missing_sequences | 连续前缀至最大已接收之间的缺失序号，至多64项 |
| seal | 全部序号、分类、字节与正文核对一致；有任何缺口都拒绝 |

服务端ACK.transport保留stream_id/sequence/event_bytes，并增加window=64、contiguous_sequence、received_highest、missing_sequences。新事件只接受前缀+1至前缀+64，已有相同事件可以幂等重放；窗口以连续前缀为基准，不能用最大已收到序号不断向前滑动。旧无mode事件仍要求严格按序到达。

## 插件调度和崩溃恢复

最多4条事件在传输，超过1MiB的事件/JS最多占3条，保留一条小事件通道。优先最早缺口，其余优先小事件；大文件内部仍逐块传输，所有事件仍先严格持久化。达到64序号窗口后等待最早缺口补齐，不无限越过。

本地账目增加连续前缀与acknowledged_ahead（已确认但前面有缺口的序号集合），与正文清理在同一事务更新。根据本地每个经过校验的ACK推进前缀，不直接覆盖成服务端某次可能迟到的前缀值。恢复必须满足：前缀+已确认离散项+未确认项恰好覆盖所有已接纳序号，不能有重复/缺失或跨任务/流误投。旧串行账目缺少新字段时，以累计确认数初始化前缀。

一条传输失败后暂停启动新项，其他已经在途的条目允许取得有效ACK并原子清理；失败和未启动项继续保留。恢复先等待在途结束，再重试同一事件/上传ID；不会重发已清理的正文。存储失败仍保留内存并暂停，不保证磁盘失败期间崩溃可恢复。

## 分析固定输入

接收页继续使用物理接收序号分页，保证游标不因乱序补传跳过记录。分析不能直接把接收顺序当采集顺序：按每个流的transport.sequence恢复逻辑顺序，保留不同流及无流旧证据的原位置。

导出固定输入时，同时固定物理接收水位和各流在该水位的连续前缀，只复制可见前缀与其正文；selection.json记录delivery_frontiers/deferred_events。即使后来缺口补齐，再导出旧水位也不能带入当时尚不连续的事件。deferred_events>0在结果中留delivery_sequence_pending缺口；只有后到事件、前缀为空时作业显示waiting_for_sequence，不启动空分析。缺口补齐触发下一批，旧批次不改写。

连续前缀进入既有“递归收集默认5层→结算冻结→统一分析”，不执行下载的JS或探测提取出的API。静态精确绑定与Agent仍未接入。

## 验证与剩余边界

- 后端覆盖窗口上界、2先于1到达、缺口封账拒绝、冲突拒绝、服务端重启、旧串行流升级、旧水位保持不可见以及分析前等待前序数据。
- 插件覆盖大JS阻塞时小请求先ACK、三条大传输时保留小通道、超过64窗口暂停并恢复、部分ACK后重启仅补未确认、旧服务器串行回退、账目损坏拒绝恢复；实际Recorder请求/响应链路也覆盖。
- 并发调度不等于无限吞吐；64窗口耗尽会等待。SQLite仍串行提交，采集正文读取/请求收尾仍有串行阶段，CPU、磁盘与网络带宽仍受资源限制。
- 原始CDP日志持久化/重放、会话租约、长期配额/容量治理、真实MV3及目标服务器压力验收仍未完成。
