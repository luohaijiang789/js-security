# 字段路径、证据与整改判定规范

目的：确保前端 JS 跨境透传的结论能被复查，并支持 EO/DSP 问题整改。执行入口见[交付目录](../../deliverables/README.md)；本文维护两侧共同的判定规则。

## 1. 每种结论需要什么证据

| 主张 | 最少证据 | 不能替代它的线索 |
|---|---|---|
| 代码具有采集/发送能力 | 对应版本、读取/变换/发送路径与条件 | 依赖中出现某 SDK 名 |
| 某场景传输情况 | 与场景关联的具体字段/载体、网络事件/失败及必要接收证据，注明确认到哪一步 | 只看到读取、调用/排队或单个发送前事件 |
| 首跳后处理/落地 | 接收代码/配置、日志、队列/存储等相符记录 | 域名、CDN、首跳 IP |
| 某主体能够访问 | 有效身份/权限、条件、密钥/映射及组织关系 | 单条 allow、云区域标签 |
| 发生过读取/使用 | 合适的数据面或供应商证据 | 有访问能力或没有日志 |
| EO 适用与处置 | 上述事实及数据口径、主体、交易、例外等复核 | 单次出境请求、token 名称 |

代码/配置/观察必须在所判定范围内相容，不能把旧日志、新源码和另一个租户配置拼成同一事件。

## 2. 路径成立的条件

- [ ] 对象实例和属性载体存在真实传递关系。
- [ ] 分支、角色、区域、配置等条件能共同成立。
- [ ] 读取、入队、身份变化、序列化和发送的时间顺序成立。
- [ ] 实际序列化仍包含该字段或已说明的变换，检查后续改写。
- [ ] 发送属于指定运行时和配置，未混淆浏览器/SSR/Worker。
- [ ] 跨消息、存储、队列和后端的连接均有证据或明确断点。

对共享机制可以复用已证实语义，但组内调用者、配置、序列化和运行上下文差异仍需核对。

## 3. 变换与关联

| 观察/变换 | 可以说什么 | 仍不能说什么 |
|---|---|---|
| 读取字段后 token 变化 | 控制噪声后可形成输入依赖假设 | token 含原值、可恢复或已匿名 |
| 编码/压缩/普通哈希/加密 | 记录变换并继续分析接收方能力 | 自动安全或自动原值泄露 |
| 合成标记经已知链进入载荷 | 支持对应字段/变换的发送主张 | 所有场景/版本都发送 |
| token 与账号共同出现 | 需要调查关联键、稳定范围和持有方 | 仅靠共现就证明所有接收方能关联 |
| 字段被序列化过滤 | 缩窄或反驳对应出站主张 | 过滤前的队列/日志也一定无副本 |

相同字段名、端点或时间只生成匹配候选。报告分开保留“观察”“路径”“关联”，不将它们覆盖成一个事实。

### 3.1 对“发送”逐项留证

| 事实 | 支持什么 | 还需补什么 |
|---|---|---|
| 应用调用/SDK 入队 | 生成或准备发送 | 最后改写、网络请求与失败 |
| Beacon 返回 true | 浏览器接受排队 | 不证明传输成功或接收落地 |
| 请求即将发送/网络层记录 | 对应工具阶段的请求信息 | 后续阻止/失败、SW/缓存/重定向、载荷完整性 |
| 对应响应/接收端证据 | 按实际来源支持一次交互或接收主张 | 响应是否来自网络、字段是否被接收/处理，不能只看 2xx |
| 下游写入/读取记录 | 指定字段及处理/访问事件 | 不能外推其他副本、主体和时间 |

这些是分别维护的事实，不是统一证据分数；接收端先取得的证据也可独立成立。失败既可能发生在数据出站前，也可能发生在到达之后，不能仅凭 loadingFailed 判数据没出去。依据与工具限制见[Web 机制核验](../../references/03-浏览器与平台/浏览器与Web平台机制.md)。

### 3.2 区分发起者、字段写入者与接收方

同一业务请求可能同时含业务参数、SDK 风险头和浏览器自动携带字段。分别记录：最初来源、各次写入/覆盖者、最终序列化者、发送/转发者和接收入口。调用栈只支持它实际观测到的边，不能把整个请求的每个字段都归给栈顶 SDK。

同时保留原始载体引用、解码/解析版本、字段路径与变换映射。端点归一化、事件拆批和字段重命名不得丢掉原请求；只把解析失败或截断写成字段缺失，会造成假阴性。

## 4. 未发生、未知与覆盖

| 状态 | 正确记录 | 后续动作 |
|---|---|---|
| 场景没触发/无权限 | 未验证 | 补前提或账号 |
| 工具不支持/执行失败 | 覆盖缺口 | 补能力或修执行 |
| 条件成立且观察工作，但窗口内未见 | 有界未观察到 | 查采样、队列和剩余条件 |
| 找到过滤、互斥或错版本等反证 | 修改具体主张 | 保留反证与适用范围 |
| 资产/配置未取得 | 材料缺口 | 指定负责人和受影响结论 |

候选图可能误连，也可能漏掉真实路径，不是程序全部行为的完整上界。分别报告资产、机制、场景、路径和字段的分母，不能把两侧相互一致率当整体准确率。阴性结果先以正例确认观察有效。

正例要对应相关执行上下文、载体、观察时点和解析能力。主页面 fetch 正例不能证明 Worker Beacon、multipart 文件或另一 frame 同样可见；缺少对应校准时限制结论。

## 5. 调查优先级与停止条件

分别记录潜在影响、证据充分程度、补证对决策的作用与成本；不把缺少运行证据乘成低风险。

| 情况 | 动作 |
|---|---|
| 冗余字段路径已有充分证据 | 推进最小化；主体/历史调查并行 |
| 必要风控不透明 | 优先获得支持限用/保留/替换选择的事实 |
| 同类调用者大量重复 | 按共同机制调查，保留差异 |
| 缺权限/供应商资料/预算耗尽 | 明确交接和范围限制，不循环让模型重猜 |

一次调查可在主张已支持、被反驳、完成有界核查或形成有负责人的阻塞时结束；项目未结项不能因此改成通过。

## 6. 整改与复验

控制点应覆盖目标路径和已知旁路：源头构造、队列、SDK 配置、发送、后端接收/日志、区域和访问各覆盖不同问题。不要只在已知 fetch 调用删字段后宣称所有链路安全。

- [ ] 写清必要字段、受影响调用者与真实修改点。
- [ ] 查错误/重试、Beacon/Worker、旧队列和字段重注入。
- [ ] 用相容条件核对改前后实际行为，并验证必要业务。
- [ ] 接收后、历史副本、权限和供应商处置按整改目标补证。
- [ ] EO/DSP 事实和适用复核按[Checklist E/R/V](../../deliverables/项目Checklist.md)关闭。
- [ ] 记录源码/配置/供应商/权限/用途变化会使哪些结论需要重审。

模板：[发现与整改卡](../05-模板/发现与整改卡.md)。更早的详细推理保存在[研究归档](../90-历史稿/早期体系与架构研究.md)，有分歧时回到版本与原始证据复核。

## 7. 双侧反例审阅：假设案例与预期处理

以下是设计论证，不是已执行测试。执行时由独立证据或复核人给预期，不由同一 Agent 自己宣告通过。

| 案例 | 容易出现的错误 | 正确处理与后续动作 |
|---|---|---|
| 双方仅使用同一份已知 SDK 列表 | 相互一致被当全覆盖 | 保留独立快照，补远程/动态资产与未知机制 |
| 全局 request 栈顶是业务包装器，风险头来自 SDK | 请求整体误归因 | 逐字段查写入/覆盖，核 SDK 配置与调用顺序 |
| Beacon 已排队，但随后被阻止或失败 | true 被当成功透传 | 分开留调用、网络与接收证据；仍追失败阶段 |
| 改配置提高采样后才触发 | 测试行为被当生产发生 | 保留干预条件，生产主张单独待证 |
| multipart 文件未被观察器返回 | “没有字段”被当未采集 | 标载荷部分缺失，不允许通过该检查 |
| 灰度期间源码/脚本配置混用 | 拼出不存在的路径 | 按观测资产/配置分组，不能对齐的留未知 |
| 同一 /collect 含错误与回放，字段也重名 | 关联到错误事件/调用者 | 保留批次/事件/字段身份及变换、条件 |
| 敏感谓词只决定是否发常量事件 | 将控制依赖误写原值泄露 | 分开记录派生/控制信息，评估是否暴露属性 |
| A 用户事件离线入队，B 登录后才发送 | 只测单用户主流程漏报 | 保留队列身份与跨状态场景，核归属与清理 |
| 改主发送路径，但重试/回退重新加入字段 | 正常场景通过被当全部修复 | 对每个备选路径验证，检查旧队列与下游副本 |
| 把发送功能整体关掉，敏感标记消失 | 业务失效被当有效修复 | 除目标阴性外，必要诊断/风控事件必须有正向结果 |
| 两边证据皆来自同一个 Hook 推测 | 重复引用被当两份独立证据 | 标共同来源；补未干预网络/源码或接收记录 |

每个反例要导致主张、任务或验收条件变化；仅让模型再“仔细检查”不算完成反证。
