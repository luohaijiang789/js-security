# 难点与已知问题

本文解释前端 JS API 提取为什么困难，并保存已经复现的问题和修复约束。当前修复进度只看[开发计划](plan.md)，验收方法只看[测试与验收](testing.md)。

审计日期：2026-10-29（北京时间）。代码基线：主干 `7e383a0`，提取器 0.10.0，插件 0.7.1。

结论：已有源码、构建和 Excel 流程，但距离“输入典型前端仓库，可靠交付 URL、参数、Host、JS 文件”仍有阻断项。当前主要问题是资产漏扫、请求漏识别、值追踪成本过高、位置归属错误和交付膨胀。单纯提高预算、增加 AI 或接入 jshound 都不能自动解决这些问题。

## 核心难点

| 难点 | 原因 | 设计方向 |
| --- | --- | --- |
| 找全 JS | 入口、懒加载 chunk、Worker、manifest、Webpack runtime 和动态路径形成多层引用 | 独立构建资产图，逐边记录发现、失败、循环和停止原因 |
| 找到真实发送点 | fetch、Axios、SDK、自定义 client 和多层封装的调用形式不同 | jshound 负责广泛发现，绑定和客户端模型负责核验，候选不直接当接口 |
| 还原 URL 与 Host | 字符串可能分段，baseURL 可能来自实例、环境、页面或 hook | 从发送点反向做字段相关追踪，保留来源、条件和运行时未知 |
| 还原参数 | Query/Body/Header 可能由展开、别名、条件、序列化和 hook 分散生成 | 字段级抽象值和写集，不因一个未知调用抹掉整个对象 |
| 定位对应 JS | source map 可能完整、缺失或只覆盖部分内容，同内容也可能有不同资产归属 | 每个资产独立规划 map、内部模块和原始 JS，保留哈希与引用路径 |
| 控制速度 | 按入口重复分析共享依赖，函数深度和分支会造成超线性放大 | 全局解析/绑定索引、可验证的函数摘要、定向数据流和增量缓存 |
| 处理混淆与加密 | 压缩重命名通常仍可解析，控制流平坦化、eval、运行时解密可能没有静态答案 | 分级支持并明确未知；必要时结合受控观测，不能伪造确定值 |
| 使用 AI | 模型擅长识别陌生封装和解释字段，但可能生成没有证据的答案 | AI 只提出结构化建议，必须经 AST、绑定或观测证据验证后接纳 |

## 已确认的六项缺陷

以下六项均用自写最小输入复现，当前尚未修复。审计没有执行目标业务 JS，也没有请求提取出的 API。既有公开项目数据来自固定版本的 [0.10 实测](archive/releases/release-0.10.md)，不作为独立盲测结论。

P0 指直接漏接口或错误归属，阻断可靠交付；P1 指字段、范围或统计不可信，需要在下一轮修复。

| 编号 | 优先级 | 复现结果 | 直接影响 |
| --- | --- | --- | --- |
| A01 | P0 | 配置 `transport` 为 fetch 客户端，显式入口调用 `/hidden`：semantic 有 1 条，hybrid 为 0 条，语义阶段未启动 | 用户明确配置仍漏接口；发现器变成精查的单一门禁 |
| A02 | P0 | `Page.vue` 和 `Page.vue.js` 同时存在：两个候选都变成 `/plain-js`，`/vue` 消失 | 临时文件相互覆盖，接口被归给错误源码 |
| A03 | P1 | `scanFiles=['other.js']`，仍输出无引用关系的 `api.js` 中 STS 请求 | 扫描范围失效，分片结果会污染和重复 |
| A04 | P1 | Body 为 `{__unknown:'business-value',id:7}`：只恢复 id，前一个字段变为未知展开 | 合法业务字段与分析器内部状态冲突 |
| A05 | P0 | 两份构建 JS，一份有 map、一份无 map：只提取有 map 的 `/mapped`，漏 `/unmapped` | 混合产物不能覆盖；语义层还会显示 complete=true |
| A06 | P1 | 同一 JS 两处 `fetch('/one')`、`fetch('/two')` 经外部索引交付，2 条记录只有 1 个 callSiteId | 未定位候选坍缩为同一调用点，调用点统计失真 |

### A01：候选发现不能成为排他的精查入口

依据：[analyzeHybrid](../src/jshound.js) 在 `candidates.length===0` 时直接返回；有候选时，库存模式只对候选文件做语义扫描。候选来源仅包括 jshound 行、显式 URL+method/type 对象和特定 SDK 导入提示，没有完整承接自有 clients 模型。

最小反例是 `transport('/hidden')` 配合 `clients:[{name:'transport',kind:'fetch'}]`。即使指定 `entries:['api.js']`，仍返回 `semanticAnalysis.state='not-started'`，索引 coverage 却为 finished。另一个普通文件命中候选时，未命中的自定义客户端文件同样可能被排除，不限于全仓零候选。

修复要求：显式 entries 必须执行；候选集合纳入自有客户端的绑定/导入/别名与 SDK 模型；保留非候选文件的未精查状态。未知名称、动态构造仍应记录模型边界。不能简单把“索引没发现”解释为“无接口”；也不能只增加一个 transport 名字补丁。

### A02：输入规范化路径不唯一

依据：[analyzeJshound](../src/jshound.js) 将 `Page.vue` 转为 `inputs/Page.vue.js`，与真实的同名 JS 目标重合。两个输入的原始哈希不同，但 worker 实际读取的是后写入的一份代码，两份 sourceFile 归属仍被保留。

修复要求：用输入 ID 或独立序号目录保存规范化代码，明确 originalPath → normalizedPath → worker chunk 的一一映射；校验目标路径唯一。Vue/Svelte、大小写及同名生成文件都纳入测试；资产原文哈希和实际送入分析器的规范化字节哈希分别记录。

### A03：SDK 绕过统一根选择

依据：[analyzer](../src/analyzer.js) 的 entryFiles 使用 entries / scanFiles 过滤，但末尾 `sdkCandidates(program,[...sources.keys()],...)` 使用全部已解析文件。SDK 不受同样的根选择约束，也不参与同一套分区覆盖统计。

修复要求：根选择、依赖追踪和独立库存三种范围采用同一份任务计划。选中入口所调用的依赖仍可分析；本反例的 api.js 与入口没有引用关系，不应输出。确需全仓 SDK 库存时，单列范围和覆盖，不混进限定文件结果。SDK 发现与协议推断也应分别统计。

### A04：业务数据与未知状态共用字符串命名空间

依据：[values](../src/values.js) 的 `UNKNOWN='__unknown'`、hasUnknown/isUnknown，以及[字段提取](../src/request-evidence.js)跳过该键。对象类型等状态已部分使用 Symbol，但未知状态仍与业务对象混放。该问题还会影响 JSON 序列化的值与完整性判断。

修复要求：内部抽象值使用独立标签/结构或不可与业务字段相撞的状态容器；输出未知状态与用户对象分层。不能只改一个保留名称。迁移时保持交付模型兼容，并检查 `__unknown`、`__candidates`、`__multipart` 及原型相关名称的业务字段处理。

### A05：构建模式用全局互斥分支选择分析策略

依据：[analyzeBuild](../src/build-assets.js) 只要取得有效应用 sourcesContent，就全局进入 source-map-assisted，分析 mapped-sources；只有没有可用映射时才处理 Webpack 模块或原始产物。

本反例中产物清单有 2 个 JS，但只分析 1 个映射源码，语义 coverage 为 1/1、complete=true。外层确实保留了“无相邻 source map”缺口，仓库任务的 overall complete 会受该缺口影响；问题是缺口没有驱动对未映射产物的补扫，不能称整个报告都未提示。

修复要求：按资产规划 map 源码 / Webpack 模块 / 原始 JS 的补充分析。保留映射已覆盖范围，处理同一资产部分映射、vendor 和未提取模块；避免源码和产物重复计数。验收至少包括全 map、无 map、部分 map、冲突 map、同一 chunk 部分内容可映射。

### A06：未知位置被强行赋予调用点身份

依据：[交付模型](../src/delivery.js)的 callSiteId 使用源码文件、行列、业务位置等构造；jshound 原生记录没有精确行列，同文件多个候选的这些值都相同。现在得到的是一个“文件级未知位置桶”，不是一个已证明的发送调用点。

修复要求：没有位置时 callSiteId 保持未知，或使用明确标注 candidate-scoped 的独立 ID。候选 ID、调用点 ID、接口组 ID、条件变体 ID 分开，禁止用缺失位置合并真实调用。不能通过给未知位置补第 1 行来解决。

## 其他设计问题

| 问题 | 当前证据 / 状态 | 调整方向 |
| --- | --- | --- |
| 重复依赖分析与深度放大 | [B8/B9/B10](archive/releases/release-0.9.4.md)仍未完成；analyzedFunctions 按函数和入口记已分析，没有安全的调用摘要缓存 | 共享解析/绑定；纯函数与有副作用函数分别建摘要；需求驱动传播，递归采用工作列表与收敛控制 |
| 公平分区会饿死重入口 | maxSteps 按剩余分区分配；无二次回填，前面被截断后即使全局还有余额也不重试 | 分离发现和精查预算，剩余任务排队；保留未完成工作与预算原因；逐步细化而非反复从入口重跑 |
| hybrid 的改善不等于通用性能修复 | RuoYi 160 文件只精查 20；语义步数下降，但既有三轮端到端中位数约 4169→4142ms，无显著改善 | 分别测解析、索引、求值、交付时间/RSS及相同语义目标；禁止用删减分析范围证明整体算法加速 |
| coverage / complete / outcome / 退出码各表达不同范围 | coverage 主要是分区预算处理结束；模型缺口可令 complete=false，同时 CLI 仍退出 0；A01/A05 进一步暴露分母问题 | 资产、发现、选中精查、模型缺口、字段可恢复性分别统计；定义有用结果与完整性阈值，供 CI 显式选择 |
| 记录仍按上下文和分支膨胀 | [B17/B21](archive/releases/release-0.9.4.md)尚未完成；交付 snapshot 包含调用链、入口、条件，重复 occurrence 继续生成记录 | 用户总表按已定位业务调用/发送点汇总，变体另表；不丢条件组合和证据；不能把不可能同时成立的字段拼成一条请求 |
| 大报告重复嵌套且无增量合并 | delivery 同时保留 evidence.raw 和完整 sourceReport；缺少分片、跨轮合并与持久化摘要 | 小型主索引＋引用式证据分片；按 commit/资产哈希/模型版本校验合并；支持来源更新和失效 |
| 新引擎尚未打通最初的仓库地址入口 | --engine 目前在本地源码 CLI；analyzeBuild 和网站分析仍调用原 analyze | 建公共任务规划/引擎接口；源码、构建、网站保留各自资产范围和上下文；先用同版源码/产物验证复用边界 |
| “深入 JS”不是任意递归 | 仓内跨调用受 maxDepth 等约束；构建外取 1 层、网站外取 3 层，动态引用仍会未解析 | 将调用深度、引用获取深度、打包模块层级分别展示；记录每条未解析边和受影响资产，不能用一个 depth 混称全部覆盖 |
| 未解析发送点仍混在结果中 | B13 尚未迁出独立集合；外部启发式候选也不是确认接口 | API 主表、待解析发送点、外部未核验候选分区；各自计数、筛选与验收 |
| 外部候选归并证据不足 | hybrid 按文件/方法/URL/一个语义位置/已知字段覆盖关联；无法比对外部精确位置，未知载体信息留在 raw | 关联仅表示候选匹配，不提升结构完整性或可达性；来源不丢，支持拆分回查；增加冲突/错归并反例 |

安全缓存不能只用函数 AST 节点作为键：至少考虑参数抽象值、this、闭包/模块状态、客户端默认配置及 hook 状态、模型版本。摘要应包含返回值、对象字段写集、请求模板和未解析副作用，再映射回当前业务调用点。否则性能改善会换来错误 Host、跨调用参数串线及调用点坍缩。可沿用已核对的 [CodeQL / TAJS / Jelly 思路与 jshound 实际采用记录](internals/research/jshound.md)，不能把参考算法写成已经实现。

## 能力边界

1. **自动构建有价值，但不能成为唯一分析基础。** 构建会做 tree shaking、环境替换和打包；源码能补充未保留的调用，产物能证明部署形态。两路保留版本/配置/环境和位置关联，标清源代码候选、产物候选与实际请求。
2. **Host 无法对任意前端代码保证静态恢复。** location、运行时下发配置、网关重写、缺失环境值及 hook 都可能决定最终 Host。应同时保留原始 URL、baseURL、有效地址、Host 来源及未知原因。开发代理、CDN 下载域名不能冒充实际请求 Host。
3. **参数名、结构、值、最终发送阶段分开。** 查询串、Query 对象、JSON/FormData、headers、实例默认值与 hook 都需要合成依据。字段已知不代表值已知，构造字段不代表请求最终一定携带；任意加密、eval、动态代码和第三方 SDK 尚不能普遍处理。
4. **框架兼容不等于请求语义兼容。** 能解析 Vue/React/TS，只证明读到了脚本。请求封装的导入/重导出、模块解析、构建插件、编译 runtime、服务注入和生命周期需要分别验证。Monorepo、多环境和自定义构建仍需任务配置，不能承诺任意仓库零配置。
5. **AI 适合加释义和辅助建议。** 当前 [AI 适配器](../src/field-ai.js)主要接收字段路径与文件名，不恢复调用链，也不补造 Host/URL。真实模型质量尚未验收。模型可辅助提出客户端契约/字段释义候选，但需静态或观测证据核验，不能给未知值补一个看似合理的答案。
