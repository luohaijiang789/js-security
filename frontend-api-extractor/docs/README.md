# 前端 JS API 提取文档

本目录只维护一条主线：**输入前端仓库 → 固定版本并构建 → 递归发现 JS → 提取 URL、参数、Host、对应 JS 文件**。方法、源码位置、条件、证据和缺口用于解释这四项结果。

## 阅读顺序

| 顺序 | 文档 | 回答的问题 |
| --- | --- | --- |
| 1 | [目标](goal.md) | 输入和输出是什么，什么才算完成 |
| 2 | [设计](design.md) | 构建、嵌套 JS、请求还原和 AI 如何配合 |
| 3 | [难点与已知问题](challenges.md) | 为什么难，当前具体卡在哪里 |
| 4 | [开发计划](plan.md) | 已实现什么，下一步按什么顺序做 |
| 5 | [测试与验收](testing.md) | 测什么、怎么测、达到什么条件才通过 |
| 6 | [使用指南](usage.md) | 0.10.0 当前可以怎样运行和查看结果 |

## 目录边界

- `internals/`：0.10.0 及更早实现的内部机制，按流水线、分析、交付、验证和外部研究分类。它是实现参考，不是第二份计划。
- `archive/`：旧计划、版本报告和历史样本记录。只用于追溯，不在其中追加当前任务。
- 当前状态和勾选只维护在[开发计划](plan.md)；测试结论只维护在[测试与验收](testing.md)。
- 新发现的问题先写入[难点与已知问题](challenges.md)，确认修复顺序后再进入计划。

跨白盒和黑盒共用的结果语义放在主仓库的[总方案](../../docs/overview.md)与[结果和 Excel 协议](../../docs/delivery.md)。本目录不重复维护浏览器插件规格。

## 维护规则

一次迭代应从计划选择有限任务，补最小反例和固定公开样本，再实现、测试并更新实际状态。`[x]` 只表示限定范围已经实现且验证通过；方案写完、测试数量增加或候选变多都不能代替能力验收。

第三方参考源码放主仓库 `references/repos/`；外部仓库、依赖、构建产物和大报告放忽略目录 `work/`。新增语言或工具链必须写明锁定版本、安装方式和复跑命令。
