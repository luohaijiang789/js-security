# 白盒技术路线讨论：先比较，不预设选型

**当前范围：M1～M5 前端 API 与请求参数提取，不按 Host 筛选，不做敏感性或合规判断。** 以下候选尚未做原型或实测，研究范围以[主方案](../docs/前端代码仓JS请求API采集.md)为准。

## 1. 候选路线

| 路线 | 可能擅长的工作 | 主要缺口 / 要补什么 | 怎样判断是否值得用 |
|---|---|---|---|
| A：Grep + AI 定向阅读 | 快速找 请求/配置/字段线索；AI 阅读封装与参数构造 | 检索漏召回后 AI 也可能看不到代码；跨文件上下文、稳定性、引用和大仓成本需控制 | 与人工标注比较：动态地址的请求能找回多少，字段能否追对，复核成本多大 |
| B：AST + 定向程序分析 | 按作用域定位调用、提取对象结构和位置，分析可支持的拼接/封装 | AST 本身不解决模块/调用/数据流；绑定、求值、别名、副作用和库模型需要实现或复用 | 对比直接请求到多层封装的增量开发量，动态对象能保留多少可靠结构 |
| C：CodeQL 自定义查询 | 利用已有代码数据库、局部/全局数据流与库建模能力做跨文件关联 | 不是开箱输出本项目接口表；仍要定义请求、配置、参数和 SDK 模型，评估查询成本及部署使用条件 | 同一批 地址/对象/注入样例，查关系的收益能否覆盖建库、查询与模型适配成本 |
| D：分阶段组合 | 例如检索/AST 提候选，CodeQL 分析难追踪关系，AI 理解封装或提出模型 | 前级筛选可能漏掉后级永远看不到的路径；对象/位置/条件必须能对齐，工程复杂度也会增加 | 比较每加一层实际补回什么、增加多少成本；不能因堆了工具就认为更完整 |

表中是设计判断，未证实哪条更快或更准。组合路线也只是候选，不能默认 A→B→C 全上。

## 2. 有必要分清的能力层

| 层 | 要解决的问题 | 不应混淆 |
|---|---|---|
| 发现 | 哪些文件/表达式可能相关 | Grep 未命中不能当没行为，必须有发送点/黑盒等补充入口 |
| 语法 | 哪个调用/字段写在什么位置 | AST 不是数据流或运行结果 |
| 程序关系 | 字段如何跨变量、函数、对象和模块传递 | CodeQL 也需要具体分析配置与模型，候选流还要核条件 |
| 语义理解 | 封装如何传递参数、哪个 SDK 行为需补模型 | AI 的合理解释不是确定的程序关系 |
| 运行事实 | 该场景实际用了哪个地址/字段 | 黑盒实例不能代表所有配置和未触发场景 |

CodeQL 会抽取源码关系并建立供查询使用的分析数据库；建库、定义查询和解释结果都是路线成本的一部分。[CodeQL 官方概览](https://codeql.github.com/docs/codeql-overview/about-codeql/)

## 3. 高效提取有哪些可试的想法

- **缓存公共机制**：同一个请求封装只分析一次，再核每个调用的参数/配置差异；缓存绑定 JS 版本，防止复用错语义。
- **优先解决能改变结果的未知**：先追未知 Host、整体 payload 和自动注入；已能列字段时不强求实际用户值。
- **缩小 AI 输入但保持召回入口**：提供调用链、构造片段、导入和配置，不只截取 grep 命中附近几行。
- **按缺口使用重分析**：简单请求是否由轻量方式处理，跨模块副作用是否值得交数据流引擎，需实测分界。
- **复用黑盒线索**：接口/栈/参数可作为另一种分析起点；原有白盒独立发现仍保留，避免只解释已知请求。

对比方法统一见[Checklist](../docs/验证计划.md)，地址/动态参数问题见[问题清单](难点与待解问题.md)。

## 首轮建议

先验证 AST/符号解析、有限跨过程追踪与请求机制模型的组合，AI 定向辅助未知封装。以跨文件 `report(data)` 能否还原实参字段为首题；CodeQL 作为对照方案，依据实测决定是否值得引入。这里的有限追踪服务于地址和字段构造，不要求继续追到用户数据最早的来源。
