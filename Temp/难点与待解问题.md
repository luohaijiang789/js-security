# 难点与待解问题

**难的不是“JS 层数多”，而是实现缺失、运行时可变，以及对象/时间/条件容易误连。** 下表是设计需要处理的机制，不是目标仓库的实际发现。

## 1. 漏报和误报分别怎样产生

| 场景 | 容易错在哪里 | 应对与无法完成时的出口 |
|---|---|---|
| 闭包、回调、高阶函数、递归封装 | 只按函数名字连线，找错真实调用者 | 核绑定、参数、闭包及具体调用点；未知分派留候选 |
| import 别名、重导出、路径映射 | 找不到实现或把声明文件当运行代码 | 按构建/模块解析与实际文件核对，留解析失败；参考 R04 |
| 对象 spread/assign、解构、计算属性 | 漏默认上下文，或把同名属性当同一对象 | 属性路径、对象身份和未知键分别追踪 |
| 参数对象被原地修改、单例共享状态 | 只追返回值，漏请求头或上下文副作用 | 核写入、覆盖、引用共享与生效时序 |
| 拦截器、fetch/XHR 包装、SDK 安装顺序 | 业务调用未带字段，却在最后被加上 | 找安装、匹配、覆盖/删除、卸载与备用路径 |
| 浏览器自动 Cookie/Referer、资源加载 | JS 没显式读取却随请求携带；脚本加载本身也可能传信息 | 核资源 URL、凭证/策略与实际请求；不要编造 JS 读取链，也不要仅审 fetch/body |
| 依赖被打包、external、CDN 全局库 | 默认忽略 node_modules 或 vendor，漏主要采集逻辑 | 盘依赖实际实现、构建外置规则与远程代码；参考 R05 |
| 微前端、标签、动态加载 | 宿主仓扫描完成，被当整个页面完成 | 记录远程入口/配置/实现断点；补材料或交外部责任方 |
| JSX/Vue 模板、内联事件、生成客户端 | 只扫描 .js，漏脚本块或生成产物 | 盘支持文件类型与生成步骤，不支持部分显式留账 |
| bundle 压缩与 source map | 函数名变化、错误 map 对错版本、map 本身没源码 | 核产物身份、映射与源内容；缺 map 仍可查产物，不能伪造源码位置；参考 R06 |
| 异步、定时器、Promise、事件总线 | 调用栈与真正采集/写入时刻不同 | 联合查生产者、存储/消息载体与消费者 |
| 队列、账号切换、离线重试 | 当前对象已清理，旧副本仍发送 | 区分引用/副本、入队身份、持久化与 flush 条件 |
| iframe、Worker、SW、postMessage | 把消息发送当网络出站，或漏接收侧再发送 | 标执行上下文和消息字段，继续追接收侧；实现不在仓则交接 |
| JSON.stringify、toJSON、过滤器 | 对象含字段被误判最终发送 | 核最后一次覆盖/删除与序列化，保留过滤前副本调查 |
| 编码、加密、哈希、opaque token | 找不到原值就判安全，或凭 token 名猜内容 | 原值/派生/控制信息分开；核输入、输出、用途和映射材料 |
| URL 拼接、区域开关、动态目的地 | 不同分支拼出不存在的跨境路径 | 保存表达式/候选和联合条件，配置未知交黑盒或发布方 |
| eval/Function、WASM 调用、反射/Proxy | JS 的静态实现或调用目标不可确定 | 查 JS 边界与输入输出，不拉非 JS 实现；未支持的明确留账 |
| 测试/SSR/浏览器代码混杂 | 测试请求或服务端调用被当浏览器线上行为 | 标运行归属、入口和构建条件；不凭目录名直接排除 |
| 黑盒归并、脱敏、调用栈缺失 | 丢细节后强行匹配；把发送者当所有字段来源 | 按原始请求/字段关联，标信息限制；沿可用材料反查 |

资料编号见[参考资料](参考资料.md)。

## 2. 尚需讨论的决定

| 优先级 | 问题 | 决策依据或所需材料 |
|---|---|---|
| P0 | 单仓首先要交付接口清单，还是字段路径？ | 建议接口清单作入口，关键字段路径作可整改交付；用一条真实请求试跑 |
| P0 | 哪些运行代码能取得？ | 框架/构建方式、锁文件、部署对应、SDK/远程入口、已有 bundle/map |
| P0 | “追到哪里”为完成？ | 字段到最终载体/目标有依据；未知实现止于断点；国家与下游事实另补 |
| P0 | 大仓怎样控制时间和费用？ | 先覆盖发送与加载入口，再按字段/公共机制定向；记录跳过范围，不固定深度后声称完整 |
| P0 | 扫描引擎选哪个？ | 用相同正反例比较语法/跨文件/副作用覆盖、错连、成本、部署与许可，不先选品牌 |
| P1 | 外部库拿不到实现时如何整改？ | 已知调用/注入/用途能否支持限用；缺什么会改变保留/替换决定 |
| P1 | 怎么避免同一问题循环让 Agent 解释？ | 固定材料/主张、引用与停止条件；新版本/配置或证据出现才重开 |
| P1 | 整改后怎样证明业务正常？ | 配对验证目标字段不再传输和必要业务成功，补队列/重试/下游 |

## 3. 先准备的最小反例集

以下仅为纸面设计，未编写或运行样例；每例需要独立预期，不能让 Agent 自己出答案再自评。

| 样例 | 正例与反例要区分什么 |
|---|---|
| 跨模块请求封装 | 入参进入发送体；同名但不同对象不应被误连 |
| 默认上下文与属性覆盖 | 自动追加 pageUrl；最后被删除/替换时缩窄主张 |
| SDK 全局注入 | 匹配 API 加头；排除 API 或安装前请求不加头 |
| 动态加载/外置依赖 | 取得实现可追内部；缺实现时正确停在加载边界 |
| 回调与副作用 | 参数经回调或对象修改进入后续发送，不能只追返回值 |
| 账号与旧队列 | A 入队、退出、B 登录、再发送；清当前对象不等于清旧副本 |
| 互斥区域配置 | 来源与发送条件可同时成立才支持，不把两分支强拼 |
| 派生与控制依赖 | 原值进入载荷、原值转 token、只决定是否发常量事件分别标记 |
| 构建与 map 错配 | 对应产物可映射；同名旧 map 不能生成确定源码引用 |
| 整改与重注入 | 主路径已过滤，但拦截器/重试补回；功能整体停止不算兼顾必要业务的修复 |

评价分别记录：资产取得/解析缺口、路径定位正确性、漏边/错边、合理返回未知、定位成本。双侧一致率或命中数量不能单独代表整体效果。
