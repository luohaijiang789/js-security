# 前端代码仓分析工具评估

目标是对未编译、可能缺配置的 JS/TS 仓库发现请求，提取地址、方法和字段，并保留跨文件调用及未知项。现成工具能覆盖部分能力，但都不能直接产出本项目要求的完整资产表。

## 1. 候选比较

| 候选 | 已核实能力 | 主要缺口 | 结论 |
|---|---|---|---|
| [jsluice](https://github.com/BishopFox/jsluice) | Tree-sitter 解析 JS；识别 URL 使用点、fetch/XHR 等模式；输出 URL、Method、Header、Query/Body 容器和源码片段；支持自定义 matcher | 以单文件局部结构为主；纯动态 URL 会漏；已读 fetch 分支不提取 body；跨文件封装、实例、拦截器和未知对象需自研 | **A：轻量 M2/M3 基线**，也适合部署 JS |
| [CodeQL](https://github.com/github/codeql) | JS 标准库已有 `ClientRequest` 模型；可取 URL、Host、数据节点；明确建模 fetch、Axios/实例、request、got 等；具备数据流基础和扩展入口 | 需写资产查询和结果导出；对项目构建/模块解析仍要验证；CLI/引擎与查询库许可证不同 | **A：技术能力基准**；闭源仓使用前先确认 CLI 商业许可 |
| [Joern](https://github.com/joernio/joern) | `jssrc2cpg` 用 Babel 解析 JS/TS 并生成代码属性图；含 import resolver、type recovery 和 call linker 等后处理；Apache-2.0 | 没有核实到可直接产出前端请求资产的成熟模型；需自行编写请求库模型、查询和字段展开；部署与资源成本较高 | **A/B：开源跨文件路线对照**，不预设优于轻量方案 |
| [Semgrep](https://github.com/semgrep/semgrep) | 支持 JS/TS/JSX/TSX，规则易写，适合快速识别标准发送形态和封装候选 | 官方 README 明确 Community Edition 在安全场景主要受单函数/单文件边界限制；跨文件/跨函数能力属于更高级产品能力 | **B：规则与召回基线**，不单独承担 M4 |
| [LinkFinder](https://github.com/GerbenJavado/LinkFinder) | 美化 JS 后用正则发现 endpoint/parameter 文本；可处理文件、URL、目录和 Burp 输入 | 文本命中不是发送行为；不能可靠恢复 Method、实例、最终载荷或跨文件关系 | **B/C：URL 候选对照** |
| [xnLinkFinder](https://github.com/xnl-h4ck3r/xnLinkFinder) | 可从 URL、目录、HAR、Burp/ZAP/Caido 输出等发现 endpoint、潜在参数和 secret；支持递归请求和范围控制 | “潜在参数”不等于某次请求发送字段；递归模式会主动访问目标；仍以文本/响应发现为主 | **B：候选补召回和多格式导入参考** |

## 2. CodeQL 为什么值得优先验证

固定提交 `5be6d864800f` 的 `javascript/ql/lib/semmle/javascript/frameworks/ClientRequests.qll` 已提供本项目需要的几个关键抽象：

- `ClientRequest.getUrl()`、`getHost()` 和 `getADataNode()`；
- fetch 的 URL、header、body 数据节点；
- Axios 直接调用、`axios.create()` 实例、`baseURL`、`data`、`headers` 和 `params`；
- request、got、needle 等库模型；
- 通过扩展 `ClientRequest::Range` 添加自定义请求 API。

这比从零建设全仓调用图更贴近项目目标，可以用来验证“有限数据流 + 请求机制模型”是否成立。但它仍不是现成资产收集器：我们要补 Method、字段路径展开、拦截器改写、证据状态、预算和 Excel 映射。

许可是硬约束：`github/codeql` 查询库是 MIT；其 README 明确 CodeQL CLI/引擎位于另一仓库、单独许可，并指出分析闭源代码可能需要商业许可。因此在内部前端仓场景中，只能先作为技术基准，不能未核实许可就定为默认引擎。

## 3. Joern、Semgrep 与 jsluice 的位置

Joern 的价值是提供 Apache-2.0 的 JS/TS 代码属性图路线。固定提交中 `jssrc2cpg` README 明确它是 Babel-based JS/TS parser；源码也存在 JavaScript import resolver、type recovery 和 call linking。它适合回答“我们是否能在完全开源栈上实现必要跨文件追踪”，代价是需要自建较多领域模型。

Semgrep 更适合快速编写请求机制规则、识别未知封装入口和生成正反例。Community Edition 不应被当成跨文件参数恢复引擎；若要比较 Pro 能力，需把价格、代码处理方式和许可单独纳入决策。

jsluice 的接入成本最低，适合作为轻量基线和单文件部署 JS 提取器。固定提交 `0ddfab153e06` 已读源码显示：fetch matcher 会取 method/header，但没有取 body；纯表达式 URL 可能被过滤。因此我们需要保留“发送点已找到但地址未知”的记录，并补 fetch body 与字段展开，不能将 jsluice 输出直接称为完整资产。

## 4. 推荐原型组合

首轮用同一组代码运行四条路径：

1. jsluice：测单文件请求识别和低成本基线。
2. Semgrep CE：测规则开发速度、标准机制和封装候选召回。
3. CodeQL：测跨文件实参、Axios 实例/baseURL 和数据节点提取，同时记录建库与查询成本。
4. Joern：测完全开源条件下 import、调用连接和自定义请求模型成本。

统一比较：请求调用上下文召回、误报、Method/地址恢复、Query/Header/Body 字段、未知项是否保留、每个结果能否回到代码位置、许可证和运行成本。

## 5. 暂不作为核心方案

- Noir 主要提取应用暴露的服务端路由，不等同于浏览器出站请求。
- Arjun 通过主动探测发现服务端接受参数，不能证明前端代码发送过这些字段。
- 仅靠 URL/正则搜索无法满足实例隔离、参数改写和字段完整性要求，可作为补召回而非主证据。
- 通用全程序分析平台如果需要先完整构建项目、安装全部依赖或执行目标代码，与当前轻量边界冲突，应在验证中明确剔除或降级。
