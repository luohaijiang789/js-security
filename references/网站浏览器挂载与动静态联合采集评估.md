# 网站浏览器挂载与动静态联合采集评估

核查日期：2026-10-22。目标操作是：打开网站、登录、开启采集、正常操作页面，同时取得真实请求和已收集 JS 内尚未触发的请求候选。

**已有这种工具。默认优先验证传统 Burp/Yakit 代理与响应分析工作流，详见[传统工具链评估](传统前端信息收集工具链评估.md)。** 本文保留 EASYapi/ExecEndpoints 等轻量挂载候选和 jshound HAR 分析实验；它们不再是默认首选。本次检查 README 和关键源码，并跑了 jshound 的离线小样例；没有在用户实际站点验收任何插件，不把项目宣传中的“全部”“零误报”作为结论。

## 1. 推荐顺序按用途区分

| 工具 | 怎么使用 | 捕获真实请求 | 静态读 JS 补未触发候选 | 参数能力及主要限制 | 建议 |
|---|---|---|---|---|---|
| [EASYapi](https://github.com/gsubigya/EASYapi) | 加载 `extension/chrome`，目标页点 Start capture，刷新并操作；也有 Console 脚本版 | 页面 Hook fetch/XHR/Beacon/WebSocket | 已加载/内联 JS 的正则 URL/路径引用 | 真实调用可取头、Body、Query；静态候选一般只有路径，Method 未知；Worker 不覆盖，跨域脚本可能被 CORS 阻断；默认最多 60 个脚本、每脚本 300 万字符/400 引用；正文有截断预算 | **轻量联合插件试用候选**；项目较新，源码未见明确根 LICENSE，先验证、不直接复制集成 |
| [ExecEndpoints](https://github.com/execiq/ExecEndpoints) | 启动本地 Python 服务，加载 Chrome 扩展，登录后 Send；也有 attach 捕获入口 | CDP Network，真实 Method/头/Body/Query/响应 | 扩展与本地服务解析 JS、chunk、模板路径和调用点 | 正则及启发式；硬编码同站点域名过滤；Send 最长 15 秒；默认加入 Wayback，并有未受 passive 开关保护的 GraphQL 探测 | **形态贴近但默认不采用**；需先改造范围、主动行为、历史污染和采集周期 |
| Burp Suite + [JS Miner](https://github.com/PortSwigger/js-miner)/[GAP](https://github.com/xnl-h4ck3r/GAP-Burp-Extension) | 浏览器使用 Burp 代理，正常登录操作；插件分析 Proxy/Site Map 中的 JS | Burp 代理历史保存实际流量 | JS Miner 被动找 API 端点、source map；GAP 提取潜在链接/参数 | 已发送参数来自流量；未触发静态参数是线索，无法等同于完整请求结构；具体被动 Scanner 能力核对 Burp 版本/许可 | **已有 Burp 团队的首选稳定工作流** |
| [Vespasian](https://github.com/praetorian-inc/vespasian) | CLI 驱动浏览器，或导入现有 HAR/Burp/mitmproxy，再运行 JS analysis | 自有 headless 浏览器或导入流量 | 捕获 bundle/source map 的静态端点、拼接 URL、Body 字段 | 可按 `source` 区分观察与候选；不是挂到现有登录标签页的插件；静态 Header/跨文件语义不完整；默认 JS 单 bundle 5 MB、500 候选、5 秒预算 | **批处理联合分析基线**，生成时显式关闭 probe |
| [jshound](https://github.com/AmbitSecurity/jshound) | URL CLI 或本地目录；浏览器 HAR 可先转换为本地脚本目录 | 本身不捕获真实流量 | AST/模块与封装分析，恢复 URL/Method/Header/Body/GraphQL/RPC | 在线模式不继承浏览器登录；离线只分析已取得文件；导出有已确认损失，不能只读 JSONL | **结构恢复主候选**，需配浏览器收集入口 |

EASYapi 的插件版和 Console 版不能混为一谈：插件版可跨刷新/导航保持任务，Console 版刷新即丢失 Hook。两者均不是网络层全量 CDP 采集器。

EASYapi 也有候选评分、静态噪声域过滤和长度预算。其正文默认只保留短片段，导出 Header/Body 还需启用 Include headers and bodies，不能按原始请求无损归档工具验收。

ExecEndpoints 的 README 声称默认被动，但 `server/execendpoints.py` 的 `discovery()` 在 Wayback 步骤后遍历多个常见 GraphQL 路径并调用 `graphql_introspect()`，未检查 `passive`；该函数以 POST 发送 introspection 查询。本次以源码为准，不采用 README 的被动保证。

## 2. 只想打开网页点插件扫描 JS

| 插件 | 适合做什么 | 已核查边界 |
|---|---|---|
| [FindSomething](https://github.com/momosecurity/FindSomething) | 安装后从页面与引用资源提取域名、路径、URL 等线索，结果可回指来源 | 文本/正则匹配，不是完整请求参数分析；后台会额外 GET 引用资源且 `credentials: include`，不能描述为绝无额外请求；未见完整 chunk 递归模型 |
| [JS Recon Buddy](https://github.com/TheArqsz/JSRecon-Buddy) | 点击 Analyze full page，查看内联/外链脚本、端点/路径、GraphQL、source map；JSON 导出和来源位置清楚 | 核心是正则扫描；主要从 DOM 的 script 列表取得外链并重取正文，不能保证收齐所有动态 import；单内容上限 5 MB；不负责真实 HTTP 请求全量捕获 |
| [SnowEyes](https://github.com/SickleSec/SnowEyes) | 动态内容、嵌套 JS、Webpack 资源发现，中文界面 | 后台补取正文使用 `credentials: omit`；网络脚本列表有 hostname 检查；登录保护 JS、CDN 和未知 chunk 可能漏；README 提示深扫误匹配和大站卡顿 |
| [HAPPY-JS](https://github.com/MY0723/HAPPY-JS) | 整合静态扫描、动态 DOM、深度 JS/chunk 扫描及可选 Hook，中文界面 | 静态部分以正则为主；集成反调试、修改运行时、路由守卫等非采集功能，须保持关闭以免改变观测；README 说明部分较新版本另行收费，公开版本与产品功能不能混用 |

这些插件适合快速侦察。它们找到 `/api/users`，不代表已经还原该接口的 Method、Header、嵌套 Body 和所有调用条件。静态结构恢复应另用 jshound 等引擎对照。

## 3. jshound 是否满足我们的需求

### 能满足的部分

- 公共网站：读取入口 HTML、JS 和可识别的懒加载 chunk，分析未执行函数中的请求。
- 已取得脚本：本地目录离线分析，不必再访问网站。
- 结构恢复：可识别 fetch/XHR/Axios 等调用、Header、嵌套 Body、部分 Query、封装和模块绑定。
- 保留未知：未解析基址和动态字段可保留占位符；结果可带页面/文件来源。

### 不能单独满足的部分

- 没有 Chrome 扩展，不会附加到用户现有标签页；没有直接导入现有浏览器 Cookie/storage state 的公开 CLI 选项。
- 给登录页 URL 直接运行，不会自动取得登录后才返回的脚本，也不执行页面运行时插入脚本。
- 目录模式只分析现有文件，不会继续联网补抓 HAR 未包含的 chunk。
- `--max-chunks` 是数量预算，不等于本项目要求的三层 JS 父链；目前需要额外控制器。
- 官方包标为 `0.1.0`/Beta，不能按长期成熟成品评价；不保证全语言语义、SDK、动态配置和全部字段。
- 请求输出还可能混入客户端路由候选；源码 `requests_only()` 会将 `route` 类型转换为 GET endpoint，导入我们模型时必须保留发现依据，不能都当已定位网络发送点。

### 本次确实运行了什么

固定提交 `f34f9c5dcfa0`，Node v24.19.0，在离线模式执行：

| 样例 | 观察结果 | 可支持的结论 |
|---|---|---|
| 项目自带 `examples/demo-app` | 输出 6 条请求候选，包含动态基址和 multipart Body | 本地目录和多种机制路径能运行，不代表实际站点召回率 |
| 项目自带 Header fixture | 输出 4 条请求，包含对象 Header、`new Headers().set`、Axios client Header 和 XHR Header | 有结构提取能力，超出仅搜索 URL 的工具 |
| 自建合成 HAR：只有 JS 响应正文，其中包含从未调用的 `neverCalled()` 函数 | 转换后识别到 POST、页面相对地址、`X-Tenant`、嵌套 Body | HAR 中收集到 JS，即可静态发现其中未触发的 API；无需 HAR 里已有该 API 请求 |

合成函数为：

```javascript
export function neverCalled(userId) {
  return fetch('/api/untriggered?mode=preview', {
    method: 'POST',
    headers: {'X-Tenant': 'demo'},
    body: JSON.stringify({userId, context: {source: 'dashboard'}})
  });
}
```

同一运行也暴露了导出缺口：内部分析记录有 `query_schema: mode`，OpenAPI 有 Query 参数 `mode`，但 `requests.jsonl` 不含该 Query 字段且 URL 已去掉 Query；JSONL 保留了嵌套 `context.source`，OpenAPI 却将 `context` 输出为 `{}`。因此导入器需比较内部 `analyze()` 记录、JSONL 和 OpenAPI，不能任取一种就声称字段齐全。以上都是合成/项目 fixture 结果，没有用户真实站点扫描结论。

## 4. 当前最可控的组合：浏览器采集 + HAR + jshound

1. 先开 Chrome DevTools → Network，选 **All**、开始记录、开启 Preserve log，再登录并操作目标页面。
2. 把要覆盖的业务模块逐个打开，让相应 JS/chunk 实际加载。
3. 导出**包含响应正文**的 HAR；检查 JS 条目的 `response.content.text` 确实存在。Preserve log 只保留导航记录，本身不保证导出正文。
4. 用下面命令把 HAR 中的 JS/HTML 等正文落到目录，再进行离线分析：

```bash
# 安装 jshound 后，在同一 Python 环境执行
python -m jshound.fromhar session.har -o collected-js
jshound collected-js -o static-result
```

当前主 CLI 不支持 `jshound from-har ...` 子命令；仓内 `fromhar.py` 文档字符串仍写旧用法，本次已用 `python -m jshound.fromhar --help` 和合成 HAR 验证正确入口。

5. 原始 HAR 作为实际观察保留；`static-result` 标为网站 JS 静态候选。HAR 提取的请求与从 HAR 中 JS 恢复的候选不能混为一个证据来源。
6. HAR 没有的 chunk 不会自动补出；需要后续操作加载、保存同版静态文件，或由独立获取器在范围和深度约束下补取。

真实请求和静态分析可以在一个产品界面里并行完成，也可以先捕获再批量分析。后一种已可用，而且更容易定位到底是 JS 未收集、引擎漏分析还是导出丢字段。

## 5. 如何回答“JS 内部所有 API”

验收时应拆成：JS 获取是否覆盖目标范围、静态请求召回、字段恢复、实际操作覆盖四件事。尚未取得的脚本、完全动态的 URL、远程配置、加密/混淆、Worker 和第三方 SDK 都可能留下缺口。

本项目当前推荐：

1. 默认先用 Burp Proxy + JS Miner/BurpAPIFinder 被动提取，原始历史核对插件筛选；Yakit 作平台对照。
2. 需要较深静态字段分析时，使用浏览器 HAR + jshound，并处理本次发现的导出缺口。
3. 轻量浏览器体验候选保留 EASYapi/FindSomething，同时核对 Network/HAR，不直接认定其全量。
4. ExecEndpoints 进入改造候选，但硬编码域名过滤、有限捕获窗口、GraphQL 主动探测、历史来源和正则模型未解决前，不作为默认实现。
