# 浏览器请求采集工具评估

目标是由 Chrome MV3 插件在测试人员正常操作时采集真实请求，记录 URL、Method、Header、Query、Body、页面、发起脚本和可取得的调用栈，并支持过滤、持久化和导出。

## 1. 核心能力应直接建立在 CDP 上

| 候选 | 已核实能力 | 主要缺口 | 结论 |
|---|---|---|---|
| [Chrome DevTools Protocol](https://github.com/ChromeDevTools/devtools-protocol) | Network 事件提供 request ID、URL、Method、Header、post data、frame、initiator、重定向和 WebSocket 帧；可用 `getRequestPostData` 补正文 | 协议事件需自行关联；不是存储、过滤或导出产品；实验字段和 Chrome 版本差异需测试 | **A：事实来源和核心接口** |
| [Chrome MV3 debugger 示例](https://github.com/GoogleChrome/chrome-extensions-samples/tree/main/api-samples/debugger) | 官方样例展示 `debugger` 权限、附加指定 tab、`Network.enable` 和接收网络事件 | 仅为最小示例，没有请求生命周期、子目标、持久化和异常恢复 | **A：插件原型起点** |
| [requestly/interceptor](https://github.com/requestly/interceptor) | 开源 MV3 扩展及 Web UI；具有流量查看、规则、Session、HAR 导入导出等完整产品形态 | 功能范围远超本项目；会修改/重放流量；API Session 的完整采集文档主要指桌面 App；AGPL-3.0，`ee/` 另行许可 | **B/C：产品和交互参考**，不直接作为代码底座 |
| [chrome-remote-interface](https://github.com/cyrus-and/chrome-remote-interface) | Node.js CDP 客户端，README 直接示例 `Network.requestWillBeSent`；支持 target/session 操作 | 面向外部 Node 进程，不是 Chrome 扩展内部 API；无法直接替代 `chrome.debugger` | **B：测试工具和 CDP 调试参考** |
| [chrome-har-capturer](https://github.com/cyrus-and/chrome-har-capturer) | 从 Chrome/CDP 生成 HAR；处理主要 Network/Page 事件和 WebSocket；可限制 POST data | 面向自动加载 URL；HAR 不承载本项目全部调用栈、采集状态和原始事件语义 | **B：HAR 兼容层和关联参考** |
| [sitespeedio/chrome-har](https://github.com/sitespeedio/chrome-har) | 将 CDP 数据转换为 HAR；MIT；适合作为纯转换组件候选 | 调用方仍需提供并关联事件；以性能/HAR 为目标，不能替代原始证据模型 | **B：HAR 转换候选** |
| Playwright / Puppeteer | 可通过受控浏览器记录网络、trace，并作为测试自动化工具 | 不符合“测试人员在既有标签页正常操作”的插件形态；不能替代 MV3 权限、后台生命周期和本地 UI | **B：自动化验收和独立对照** |
| mitmproxy / OWASP ZAP | 独立代理可记录真实 HTTP(S)/WebSocket 流量并用作服务端视角对照 | 证书、代理部署和范围控制成本高；通常缺浏览器 JS initiator stack 与 tab/frame 关系 | **B/C：独立流量核对** |

## 2. CDP 已经证明哪些字段可取

固定提交 `71ba93da82a9` 的 `browser_protocol.json` 显示：

- `Network.requestWillBeSent` 包含 `requestId`、`documentURL`、请求对象、时间、`initiator`、重定向响应、资源类型和 `frameId`。
- Request 包含 URL、Method、Headers、`hasPostData` 和可选 `postDataEntries`；当正文太长时，即使 `hasPostData=true`，postData 仍可能省略。
- `Network.getRequestPostData` 可按 request ID 获取发送正文；无正文时会报错。
- `requestWillBeSentExtraInfo` 的原始请求头来自网络栈，但并非每个请求都会触发，且与主事件没有固定先后顺序。
- Initiator 的 JS stack 只在 script initiator 且 Debugger domain 已启用时提供。
- `webSocketFrameSent` 提供出站消息帧；连接握手和消息需要分别建模。

这说明插件原理成立，也说明不能只监听一个事件。实现必须有按 request/target/session/redirect hop 关联的状态机，并对正文省略、ExtraInfo 缺失、stack 不适用、调试断开等情况分别记状态。

## 3. HAR 的正确定位

HAR 是广泛兼容的交换格式，适合导出给人工和其他工具，但不应成为插件内部唯一数据模型：

- HAR 强项是请求/响应、Header、Query、timing 和正文表示；
- 本项目额外需要 initiator stack、target/frame/session、Filter 版本、脱敏状态、事件缺失原因、原始请求组关系和中断窗口；
- 将 CDP 先压成 HAR 再分析，会丢掉部分浏览器证据和采集完整性信息。

建议内部先保存规范化原始记录和必要 CDP 证据，JSONL 为主格式；需要兼容时再用 chrome-har 或自有转换器生成 HAR。HAR 转换结果必须能回指内部 request ID。

## 4. Requestly 能借鉴什么

Requestly 的开源 interceptor 仓展示了浏览器扩展、Web UI、流量表、规则、Session 和 HAR 工作流。其文档也说明 Session 可查看 URL、Method、Content-Type、Status、Headers、Payload，并支持搜索过滤与 HAR 下载。

但它不是可直接移植的答案：API Session 的完整抓取文档标注为 Desktop App 功能；产品包含修改、mock、重放和云协作等大量非目标能力；仓库主体为 AGPL-3.0，并有企业目录单独许可。首版仅参考信息架构、网络表格、Session/HAR 交互和测试用例，不复制代码或引入其整体架构。

## 5. 推荐实现与验证路径

1. 从 Google 官方 MV3 debugger 示例扩展起步，仅附加用户选择的标签页。
2. 接入 CDP Network 与必要 Debugger/Target 事件，先建立可靠身份关联和缺失状态。
3. 用 chrome-remote-interface 或 Playwright 编写独立测试驱动；用受控服务端日志核对实际发送。
4. 内部保存 JSONL/IndexedDB 原始记录；对比 chrome-har 与 chrome-har-capturer 的事件映射后实现 HAR 兼容导出。
5. 最后加入 Filter、归并、容量控制、停止时在途处理和恢复，不让 UI/归并逻辑污染原始证据。

首轮必须实测 iframe/OOPIF、Worker/Service Worker、重定向/preflight、Beacon、文件上传、大 body、WebSocket、导航和 MV3 service worker 重启。任何工具 README 都不能替代这些浏览器版本测试。
