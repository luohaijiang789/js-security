# 成熟 API 资产收集工具总览

结论：**现成工具已经覆盖大部分黑盒流量采集、API 归并、网站 JS 端点恢复和 OpenAPI 输出，不应从零重做。** 本项目应先组合验证，再只补源码定位、调用栈、缺口状态和 Excel 映射。

这里把“已有实现”与“长期成熟度”分开：Akto、Burp 工作流和 mitmproxy2swagger 已有较长实践；Vespasian、jshound、mitm2openapi 功能很贴近，但项目较新，必须用真实样例验证准确性和稳定性。

浏览器挂载需求的补充评估见[动静态联合采集评估](网站浏览器挂载与动静态联合采集评估.md)。本次已运行 jshound 离线小样例，确认能从 HAR 的 JS 中找出未触发请求，也确认 JSONL/OpenAPI 有不同字段损失；不能将其输出直接称作完整请求资产。

## 1. 最接近完整目标的项目

| 项目 | 已实现能力 | 可直接覆盖 | 本项目仍缺 | 建议 |
|---|---|---|---|---|
| [Vespasian](https://github.com/praetorian-inc/vespasian) | Headless Chrome/HTTP crawl；导入 Burp XML、HAR、mitmproxy；保存真实请求与响应；静态分析捕获的 JS、source map、拼接 URL 和 Body 字段；生成 OpenAPI/GraphQL SDL/WSDL/proto | 黑盒一的流量资产化；黑盒二的网站加载与 JS 静态补漏；白盒构建后本地预览 | 无浏览器插件交互；不保留 CDP initiator/call stack；静态 Header/Query 和源码业务位置不足；默认生成流程含主动 probe | **A：首个端到端基线**。采集或离线生成时关闭 probe，保留 `source` 区分实测与静态候选 |
| [jshound](https://github.com/AmbitSecurity/jshound) | 从 URL 或本地构建目录发现 bundle、懒加载 chunk 和模块；恢复 fetch/XHR/Axios/API client/GraphQL/RPC；输出 Method、URL、Body、Content-Type、Header、来源页面/文件、JSONL 和 OpenAPI | 网站 JS 静态分析的大部分主流程；白盒构建产物分析 | 在线模式无登录会话和浏览器运行时脚本；源码 Commit/行列和完整调用链仍需映射；项目较新 | **A：网站 JS 与白盒产物的主候选**，直接用本地目录模式验证白盒 |
| [Akto](https://github.com/akto-api-security/akto) | 开源 API 安全平台；从 Burp、HAR、Postman、网关和云流量持续建立 API Inventory；保存真实流量结构并跟踪新端点/参数 | 持续资产盘点、流量导入、Schema/集合管理和团队工作流 | 平台比本项目重；主要面向流量和安全测试；源码分析器以外部镜像/产品方式提供，当前开源仓中未核实到前端请求还原实现；不提供浏览器调用栈 | **A/B：平台型对照**。若接受部署平台，优先 PoC；不直接假定其源码分析满足白盒 |
| [OpenAPI DevTools](https://chromewebstore.google.com/detail/openapi-devtools/jelghndoknklgabjgaeppjhommkkmdii) | 归并 Header、Body、Query 和路径参数，生成/下载 OpenAPI 3.1 | JSON API 规格生成和交互参考 | 用户反馈大量漏项；历史派生源码存在主动过滤；安装版规则尚待核对；无完整证据验收 | **B：规格生成参考**，取消优先采集推荐，见[漏采排查](OpenAPI%20DevTools漏采排查.md) |

## 2. 成熟的流量转资产工具

| 项目 | 输入与输出 | 特点 | 定位 |
|---|---|---|---|
| [mitmproxy2swagger](https://github.com/alufers/mitmproxy2swagger) | mitmproxy flow/HAR → OpenAPI 3.0 | 两遍流程先发现路径、人工确认模板、再生成；可合并多份 capture；可选 Header/Example | **A：黑盒流量归并基线**，简单且成熟 |
| [mitm2openapi](https://github.com/Arkptz/mitm2openapi) | mitmproxy flow/HAR → OpenAPI 3.0 | Rust 单文件；discover/curate/generate；过滤、脱敏、参数化和确定性输出 | **A/B：新一代转换候选**，项目较新，和原版对照验证 |
| [traffic2openapi](https://github.com/grokify/traffic2openapi) | HAR、Playwright、代理等 → 统一 IR → OpenAPI | 多输入统一中间模型，适合借鉴本项目导入层 | **B：统一导入/IR 参考**，先核实格式覆盖和准确率 |

这些工具证明“把真实流量整理成 API 清单”已有成熟做法。它们通常不记录浏览器 initiator stack，也不会保留本项目要求的每一次原始观察和缺失原因，因此应作为导入/归并组件，不直接替代证据底稿。

## 3. 安全行业常用的 Burp/JS Recon 工作流

| 项目 | 能力 | 适用方式 | 边界 |
|---|---|---|---|
| [JS Miner](https://github.com/PortSwigger/js-miner) | 在 Burp 中被动扫描 JS/JSON，发现 GET/POST/PUT/DELETE/PATCH 端点；解析 inline source map；可导出静态文件 | 测试人员已有 Burp 工作流时直接安装 | 面向初始侦察，作者明确提示误报和人工复核；主动猜 `.map` 会发请求 |
| [GAP](https://github.com/xnl-h4ck3r/GAP-Burp-Extension) | 从 Burp Site Map/Proxy History 提取潜在链接、参数和目标词表 | 补候选参数与端点召回 | “潜在参数”不等于前端实际发送字段 |
| [JS Link Finder](https://github.com/PortSwigger/js-link-finder) | 被动扫描 JS 端点链接并导出 | 轻量 URL 补召回 | 只证明字符串/链接候选，不能恢复请求结构 |

Burp 生态说明安全人员长期使用的主流程确实是：**代理记录真实流量 + Site Map 汇总 + JS 被动扫描 + 必要时转 OpenAPI**。如果团队已有 Burp，可先用这套流程产出样例，无需等待自研浏览器插件。

## 5. 对三个方案的直接影响

### 白盒：不再从残缺源码起步

仓库可以正式构建后，优先运行：

1. `jshound <dist目录>`：离线分析完整构建产物和 chunk；
2. 本地预览 + Vespasian 被动 crawl/JS analysis：观察启动流量并补静态候选；
3. source map + CodeQL/Joern：只补源码位置、业务封装、拦截器和跨文件字段；
4. 将输出映射到统一证据模型和 Excel。

这条路线把构建系统当作配置、别名、代码生成和依赖解析器，减少自研模块解析器的范围。

### 黑盒一：先试现成插件和 HAR 工作流

先用 OpenAPI DevTools、Chrome HAR、Burp 或 mitmproxy采集，再用 Vespasian、mitmproxy2swagger/mitm2openapi 和 Akto比较。只有以下需求无法满足时才开发自有插件：

- 指定标签页的一键任务边界；
- CDP initiator/call stack；
- 原始事件、重定向跳次和采集中断状态；
- 本地 JSONL、脱敏及 `api_assets.xlsx` 的精确字段契约。

### 黑盒二：已有两个高度贴合实现

jshound 是最贴近“网站入口 → bundle/chunk → 请求与字段候选”的工具；Vespasian 则把真实浏览器流量、导入格式、JS 静态补漏和规格生成放在同一管线。应以二者为主线互相对照，Katana/jsluice/LinkFinder 降为组件和误差分析工具。

## 6. 首轮 PoC 顺序

1. 对同一可构建前端，保存源码、本地 `dist`、source map 和本地预览。
2. 对 `dist` 跑 jshound；对预览跑 Vespasian `crawl`，生成阶段显式 `--probe=false`。
3. 用 OpenAPI DevTools 或 Chrome DevTools 导出 HAR，分别导入 Vespasian、mitmproxy2swagger、mitm2openapi 和 Akto。
4. 比较 API、Method、Query/Header/Body、来源文件、实际/静态状态和误报，不只比较 URL 数量。
5. 根据差距决定是否开发插件，以及 CodeQL/Joern 只需补哪些白盒能力。
